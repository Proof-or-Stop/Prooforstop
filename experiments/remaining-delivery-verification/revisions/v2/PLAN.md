## 3. Common experimental contract

Every experiment must freeze a manifest before its first scored run: case IDs, independently chosen sample/holdout membership, accepted requirements, command/argv/timeouts/selectors, test inventory, role roster, model/provider version, prompt digests, toolchain/build/runtime identity, source baseline and candidate, environment allowlist, resource policy, cache regime, host, order seed, stop rules, target and analysis method. Sign or digest manifests and preserve every amendment; changing a scored input creates a new experiment epoch. Never repair a result file or silently discard a slow or failed run.

The new baseline is 0.3.296. A baseline plus test-harness-only commit must have its source delta recorded separately. A reconstructed old policy inside current code is an ablation and must not be labeled an old released binary. Keep the same acceptance tests and workload in both arms. New adversarial controls run against both implementations; a baseline-specific missing dependency, corrupt setup, wrong command or missing result is NOT a product RED.

Use separate private Git repositories and writable build outputs inside the Lab experiment sandbox. They may contain disposable CLI-created test data; never create, copy, advance or rewrite a real project's Story state. Existing fixture adapters must perform signed state mutations through the official CLI/handlers, not direct Story JSON edits. A private lifecycle replay is laboratory evidence, not formal Story DONE. Do not symlink a writable dist or use a global CLI that resolves to another implementation for a scored Lab run.

For performance, alternate/randomize A/B order by a preregistered seed; distinguish cold preparation and warm steady-state runs. Fix model settings and external tool versions where possible; unavailable provider version pinning is a reported confounder. Independent model calls in both arms are required for causal review timing; do not reuse first/final-review outputs between arms and present that as two independent executions.

Each run writes a durable ledger with experiment/case/pair/arm/attempt IDs, workload and implementation digests, actual command + argv + cwd, monotonic start/end, UTC correlation, PID/process group, parent invocation, wait reason, resource acquisition/release, output/receipt digests, exit/signal, selector result, coverage, final acceptance verdict, retries and cleanup. CPU, RSS, disk/temp bytes, host load and model usage are separate fields. Missing fields are unknown, never zero.

Elapsed delivery time is the union/critical path from accepted task input to verified deliverable, including required plan, implementation, review, verification, evidence publication, integration/preparation and recovery. Worker-duration sums may overlap and are reported separately. Exclusive waiting categories and unclassified intervals must reconcile to the observed wall clock. Report successful completion rate and censored/failed runs alongside time. A failed RED endpoint is a reliability comparison, not a speedup percentage.

All technical safety controls are hard requirements: no false fresh PASS, missing required test, dropped blocker, weakened selector, lost history, foreign write, unsafe resource overlap or unowned process cleanup. A faster candidate that violates one fails. Unknown eligibility and undeclared inputs execute or fail closed through current rules.

## 4. Verification matrix

### V1 — Actual delivery time, attribution and long-tail evidence

**Question:** Which part of delivery is still slow after 0.3.296, and does a specific candidate shorten it without dropping work?

**Baseline:** Build a read-only cohort manifest from the latest complete 30-day interval and currently active Stories using canonical CLI reads, preserving CLI identity, authoritative worktree resolution and collection time. Freeze the date interval; include unfinished/cancelled Stories and explicitly mark missing timestamps. Do not equate `createdAt → DONE` to CPU work, exclude waiting to make the distribution faster, or rely on main's INIT_CHECK mirror for a worktree's current phase.

Current read-only preparation found that `story_resolve` may return a candidate authoritative worktree while its phase remains the main mirror. Resolve the cwd, then read `story_get` in that cwd and preserve both outputs; do not treat the resolver phase alone as the population label. An unresolved cwd or a refused legacy/bootstrap identity is an unknown/blocked row, not an inactive Story or zero duration. The observations under `census/` are data-quality/adoption leads requiring private-fixture reproduction before a repair, not a causal explanation of historical hours. The actual invoked wrapper and cwd are recorded; do not infer which implementation an existing process loaded from the wrapper path.

Use two distinct populations:

1. Controlled Lab replay of actual repository tasks with full independent implementation/review/validation against the same initial task and acceptance. This measures `T_lab`, not deployed Story lead time. Select a pilot of six tasks spanning docs/local handler/shared core/gate/validation infrastructure/known slow recovery; freeze selection before reading candidate results. Known prior cases are development controls, excluded from holdout conclusions.
2. Real Story read-only observational follow-up after integration/adoption, producing `T_actual`. Do not alter or restart these Stories from the Lab. A historical-before/current-after comparison alone is confounded by scope, model and load; stratify and show those covariates, or keep the conclusion descriptive. Randomized live causal assignment requires a later explicit rollout design; Lab replay cannot substitute for it.

**Target RED:** A current baseline task reproduces a named repeated execution, wait or recovery path with causal trace, and fails its preregistered successful-completion/elapsed acceptance. Missing end-to-end telemetry is a measurement gap first, not an invented slow-task RED.

**GREEN:** All fixed task acceptance and safety controls pass, no new missed defect, and successful paired Lab delivery improves by the frozen threshold (initial practical target: at least 20% median reduction in the targeted stratum; statistical improvement additionally needs the preregistered paired confidence bound). The 20% is a proposed decision threshold, not a measured prediction. No universal minute SLA is borrowed from dynamic-validation design prose.

V1 confirmation uses 20 new held-out task clusters per *claimed targeted stratum*, excluded from the six-task pilot and all tuning. Freeze the tasks before candidate confirmation; run exactly one independently launched A/B pair per cluster with balanced randomized order and one fixed, preregistered model seed per arm where supported. All paired runs must reach the same accepted-deliverable endpoint for the timing PASS. Failed or censored pairs remain reported and block that timing PASS; a recovered baseline failure can earn a reliability/mechanism result only. The primary estimator is `1 - median(T_green)/median(T_red)`. Before confirmation freeze a 10,000-resample paired task-cluster bootstrap (seed 20260910) and its one-sided 95% upper bound for the ratio of medians. Require the point reduction >=20% and the upper ratio bound <1. Report sample/assumption limitations; this is a bounded replay-stratum claim, not a deployment inference. Before this set and analysis are frozen and run, V1 cannot be BOUNDED_PERFORMANCE_PASS. Smaller pilots remain BASELINE_OBSERVED or MECHANISM_GREEN. If the measured pilot variance makes this design uninformative, revise the design before accessing new holdout outcomes, preserve the amendment and keep the result unproven.

Publish P50/P95 with sample size, censoring, strata and confidence intervals. Below 100 completed observations per claimed deployment stratum, report tail order statistics as exploratory and keep deployment P95 closure open; 100 is only an operational floor, not a guarantee of precision. Even above it, an interval crossing no improvement is inconclusive. Stop claiming "real Stories no longer take hours" until `T_actual` supports that claim for the explicitly named population. An ongoing deployment cohort can remain incomplete while a Lab mechanism is already proven.

### V3 — Review convergence with defect detection preserved

**Baseline:** Freeze the current first-wave/remediation/final-certification policy and actual role/prompt inputs. Keep the old seven-defect/two-clean corpus as regression controls only. Select new cases across handler, gate, state/identity, resource, test and documentation failure classes. Maintain an independent oracle of expected defects and truly clean controls, including runnable negative assertions where possible.

**Pilot:** Eight new task clusters (six defective and two clean), two independent fixed-seed runs per arm for feasibility only. Keep oracle files outside reviewer-readable roots, limit reviewers to case source and frozen prompts, and audit tool traces for leakage. Candidate reviewers cannot see baseline findings or the oracle. Separate the implementation author, review invocations and Claude's final data audit roles.

**Target RED:** The baseline policy incurs an identified avoidable wave/cost, or the candidate loses a known defect under otherwise equal acceptance. Do not manufacture a second mandatory wave if current main does not require it for that case. Record actual review transitions and final findings; action-count arithmetic alone is insufficient.

**GREEN:** Final certification and all required roles remain; all known must-detect defects in the scored corpus remain detected/resolved, no high/critical defect is newly missed, clean-control false positives do not increase beyond the frozen rule, and measured review-to-accepted-repair wall time improves. First-wave speed alone is not the endpoint.

For a wider bounded claim, use at least 60 independent held-out defective task clusters, plus a separately selected clean-control set, all separate from development/pilot cases. Every cluster in the 60-case denominator has at least one preregistered must-detect defect; clean controls never inflate that denominator. Unit of analysis is task cluster, not every role or repeated finding. With zero clusters suffering a newly missed must-detect defect, the one-sided exact 95% upper bound on that event rate is `1 - 0.05^(1/n)` (about 4.87% at n=60), under the declared sampling assumptions. This is NOT proof of zero population loss or universal non-inferiority. Also report paired recall difference, false positives, discordant clusters and intervals. A single new high/critical miss fails regardless of aggregate timing. For all known must-detect defects, any newly missed case fails the finite-corpus claim. Do not silently relax the oracle or stop after favorable seeds.

Held-out scoring uses exactly one preregistered run per arm per cluster, with no best-of-k selection or retries of a valid unfavorable outcome. Within that run, union the findings of the required roles according to the frozen defect-equivalence oracle; a cluster is newly missed when at least one oracle must-detect defect found by the baseline is absent from the candidate's final finding set. Independently, any oracle must-detect defect absent from the candidate fails finite-corpus completeness, even if the baseline also missed it. Pilot repeats do not enter this denominator. The binomial bound applies only to the fixed single-run cluster outcome and declared independent sampling model. Freeze 20 independent clean-control clusters for confirmation, use the same one-run-per-arm rule, and publish their false positives separately. An unpinnable provider seed/version remains a measured limitation, not a hidden retry allowance.

### V5 — Recovery within an explicit output/storage/trust contract

**Baseline:** Observe which real repeated commands exceed the current durable output bound or lose a recoverable publication transaction. The current >1 MiB fallback is documented behavior, not evidence corruption. Keep the existing passing short-output/lease/fencing/history controls as inherited regression evidence.

**Target RED:** In a selected supported recovery scenario, a completed command is unnecessarily run again or cannot publish despite a retained valid receipt/output and authority. Record execution count through actual subprocess launch events across the original and restarted process, not a mocked counter. If large-output fallback is a material measured cost, treat expansion of its supported bounded range as a separate scoped performance hypothesis, not "arbitrary output support".

**Matrix:** 0-byte/12,000-character boundary; minus-one/exact/plus-one at both the UTF-16 `matchingOutput.length` predicate and the actual serialized JSON byte predicate; representative 2 MiB and 16 MiB outputs; multibyte UTF-8, escapes and redaction boundaries; selectors at start/middle/end; partial write/rename; transient vs permanent ENOSPC; termination after execution before receipt, after receipt before canonical import, and during import; transferred lease; retained-anchor/missing-mirror; tampered output; missing/different key. Large-output cases are comparative characterization until their supported bound and quota are frozen. Include the achievable straddle (character count within cap, serialized bytes above cap). The reverse straddle is impossible for the string object serialized by current code: standard UTF-8 JSON encoding uses at least one byte per UTF-16 code unit plus object syntax. Record that mathematical constraint and actual boundary probes; never fabricate an impossible case to tick a matrix cell.

**GREEN has two fault classes.** Post-receipt recovery requires an already durable, authentic reusable receipt plus its required output, retained authority and matching current inputs. For these cases, restart must complete with valid independent selector/history verification, exactly one total test execution, immutable original receipt and the current owner generation. Pre-receipt faults (execution ended but no durable result exists, partial receipt write/rename, or ENOSPC before receipt persistence) require explicit safe re-execution or refusal, no fabricated PASS, no duplicate/foreign canonical publication, and preservation of any authentic receipt that does exist. Record their actual execution counts; do not assert exactly one. If commands are not safe to re-execute automatically, require an explicit recovery decision instead of replay. A durable execution journal or idempotency protocol would be a separate scoped hypothesis; this plan does not assume it can infer an unrecorded external side effect.

Exact output bytes/digests, bounded storage/memory and cleanup must be proved. If output streaming/spooling is selected, freeze a finite tested ceiling and disk quota before implementation; do not just remove the cap. One recoverable long-duration witness must use real time (including a 51-minute case only if the touched path is duration-sensitive); short injected controls establish mechanism, not long-duration reliability. The zero-rerun success denominator contains only the declared post-receipt recoverable cases. Pre-receipt and irrecoverable outcomes are reported as distinct cohorts, never silently removed from overall completion/cost reporting.

Corrupt/unavailable output without a verified backup, permanent storage loss, or deletion of all trusted history/Git objects/signing keys must produce an explicit recover-from-backup/manual-reexecute requirement and no false PASS. Deleting a recoverable mirror should recover from retained authority; destroying every authority cannot. These are separate expected negative controls, never counted as zero-rerun successes. A real missing recoverable backup is an unmet operational prerequisite, not silently "resolved by scope".

## 5. Statistics and decision discipline

Correctness gates precede performance gates. Timing fields report per-arm values, absolute delta, ratio, pair-level medians, uncertainty and completion counts. Stage percentages are never added. No speed ratio is computed from failed-to-successful endpoints. Runs that timeout remain in completion/reliability reporting and the prespecified censored-time analysis; never compare only the candidate's fastest successes.

Pilot results select a hypothesis/setting and estimate variance; they are not pooled into holdout confirmation. Before confirmation, implement and audit the analysis code on synthetic timing and failure vectors (including reversed arms, missing rows, overlapping intervals, timeout, rerun and duplicate records). Freeze the method, confidence level, one primary endpoint per experiment and multiplicity handling for multiple claimed settings. Use task/pair/session clustering appropriate to each claim; small-n intervals must remain labeled exploratory. Real Story before/after data retains confounding disclosures even if a narrow confidence interval is obtained.

## 7. Result artifact contract and completion states

Per experiment retain `manifest.json`, baseline/candidate source deltas, environment/tool identities, `runs.jsonl`, raw stdout/stderr, input/output/receipt hashes, subprocess/resource timelines, oracle and coverage manifests, cleanup evidence, analysis inputs/output, all failed attempts and Claude audit. Every result row must expose: `id`, `claimScope`, `status`, `redEvidence`, `greenEvidence`, `before`, `after`, `unit`, `coverage`, `completionCounts`, `cost`, `uncertainty`, `limitations`, `remainingPrerequisites` and evidence paths. Allowed statuses: NOT_RUN, SETUP_BLOCKED, BASELINE_OBSERVED, TARGET_RED, MECHANISM_GREEN, BOUNDED_PERFORMANCE_PASS, EXPECTED_REFUSAL_PASS, INCONCLUSIVE, FAILED, COHORT_INCOMPLETE. A plan audit PASS is not any of these product GREEN states.

`acceptance.json` is the plan-level ledger. Its `planSha256` is SHA256 of the exact PLAN.md bytes. Every edit preserves the prior plan and ledger under `revisions/`, appends the prior digest/path/reason to `amendments`, and regenerates the current digest. Every child and parent carries an explicit claimScope, limitations and evidence array. Status is computed conservatively from children by `verify-plan.mjs`: FAILED takes precedence; all NOT_RUN stays NOT_RUN; any setup block yields SETUP_BLOCKED; otherwise an unrun or incomplete child yields COHORT_INCOMPLETE. Remaining inconclusive or incomplete proof levels cannot become a combined performance PASS. Only all performance-PASS children can aggregate to BOUNDED_PERFORMANCE_PASS; mixed passed correctness/refusal/performance children aggregate at most to MECHANISM_GREEN. Every status except NOT_RUN/SETUP_BLOCKED requires nonempty evidence, including partial aggregate evidence. This validator is an experimental reporting guard, not formal Story or release evidence. Mutating a status, dropping its scope, emptying its evidence, changing plan bytes or losing amendment provenance must be rejected by self-check controls before using a report.

Each claim is separate: V1 Lab replay versus actual deployment; V2 enrolled cohort versus global census; V3 finite oracle versus wider sampling; V4 reuse versus split; V5 recoverable faults versus explicit irrecoverable refusal; V6 tested host versus portability/soak. A scope-limited success never silently ticks the broader claim. A report must state both what is solved and which listed obligations remain. The original integration gap stays CLOSED unless new evidence contradicts it.
