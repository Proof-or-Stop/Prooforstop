# 打造通用 Skill 的心得 — 从 web-debug 说起

## 核心思路：给 AI 装一双眼睛

web-debug 的本质很简单：**让 Claude 能看到浏览器里发生了什么，并且能动手操作**。没有它，web 项目对 AI 来说就是一个黑盒——代码写完了，跑起来对不对，全靠人肉验证。有了它，AI 能自己截图、读状态、点按钮、发现 bug。

实测就是最好的例子：通过 WS 桥远程下了几盘五子棋，截图发现赢家显示反了，直接定位到 `updateStatus()` 里的逻辑反转，修了，再验证——全程没需要人介入。

## 通用 Skill 的设计原则

### 1. 调试通道必须比应用代码更早、更健壮

最大的改进就是把 WS 客户端从 `<body>` 移到 `<head-prepend>`。原因很直觉：如果应用代码报错了，你的调试工具恰好在应用代码之后加载，那你就看不到错误了——最需要调试的时候恰恰调试不了。

通用原则：**基础设施层永远在业务层之前**。error handler、调试桥、监控埋点，都应该先于业务代码就位。

### 2. 架构三段论：Browser - Bridge - Claude

```
浏览器（被测对象）  <-WS->  本地中转服务  <-HTTP->  Claude（操控者）
```

为什么不让 Claude 直接连 WS？因为 Claude 的工具链是 curl/Bash，HTTP 是最自然的接口。中转服务做协议翻译，两端各用最舒服的方式通信。

通用原则：**Skill 的接口应该匹配 AI 的工具能力**。Claude 擅长 HTTP + JSON，那就给它 HTTP + JSON。不要让 AI 去处理二进制协议或有状态连接。

### 3. eval 是万能后门，不需要预定义所有 API

server 只实现了 5 个命令（eval/screenshot/click/type/stop），但 eval 让能力边界无限大——想读棋盘状态？eval 一行 JS。想注入辅助函数？eval。想检查 DOM？eval。

通用原则：**提供一个逃逸舱**。再完善的 API 也覆盖不了所有场景，一个 `eval` 入口让 AI 能自适应。这比堆砌 50 个专用 API 更实用。

### 4. 错误要主动捕获，不能等人问

加了 `window.__webtest_errors` 后，AI 每次连上就能主动查有没有报错，而不是等到截图发现页面白屏才去排查。

通用原则：**Skill 应该让 AI 能自主诊断**。不只是"能做什么"，还要"能发现什么不对"。

### 5. 坐标系文档化

踩了一个坑：`/click` 的 x/y 是视口坐标，但一开始按 canvas 内部坐标传了，结果全部落空。修复后在 skill.md 里明确写了这个注意事项。

通用原则：**skill.md 是 AI 的操作手册**，容易出错的地方必须写清楚。AI 不会"试试看"——它按文档执行，文档模糊就执行错。

## 什么样的能力适合做成 Skill？

满足这三个条件的：

1. **跨项目复用** — web-debug 对任何有 Vite 的 web 项目都能用
2. **需要多步协调** — 启动服务、打开浏览器、等连接、执行测试，不是一个工具能搞定的
3. **人机交互模式固定** — 截图→判断→操作→验证，这个循环是稳定的

反过来说，如果一个能力只用一次、只适用于一个项目、或者流程每次都不同，就不值得做成 Skill，直接在对话里即兴完成就行。

## 最后

web-debug 本质上是给 AI 做了一个"远程桌面"的极简版——能看（screenshot）、能摸（click/type）、能想（eval 读状态）。三个能力组合起来，AI 就能自己玩五子棋、自己发现 bug、自己验证修复。这比写测试用例更直觉，比人肉测试更可重复。
