# Proof-or-Stop CLI Reference

> Full command reference for the Proof-or-Stop CLI (`proof-or-stop`). For what the project is and the problem it solves, see the [README](../README.md).

Proof-or-Stop CLI 0.3.271 is the CLI-first product entry point for the Proof-or-Stop Story workflow. `proof-or-stop` is the canonical product command, pointing at the same set of project state, phase, gate, review, evidence, and handoff semantics.

This repository currently contains:

- `packages/main`: the Proof-or-Stop core CLI
- `packages/utils`: extension tools such as `aux_*`, `truth_*`, and `tool_status`
- `bin/proof-or-stop.js`: the full bootstrap entry point (`main + utils`); used only by this repository itself, and not generated by the default global-thin init for new projects
- `bin/proof-or-stop-codex.js`: the Codex-specific local entry point, which records activity as `source=codex`; generated only with explicit opt-in in full/thin mode, and not generated by default in global-thin

> **Identity contract.** `proof-or-stop` is the only npm bin and command identity.
> `bin/proof-or-stop.js` and `bin/proof-or-stop-codex.js` are the supported local
> wrappers. Retired command names do not resolve and are not generated by `init`.

## Brief-by-default outputs (agent-loop context hygiene)

The highest-volume read-only commands print a **brief** summary by default so an
agent loop does not re-pay a multi-kilobyte dump on every subsequent model call
in the same turn. This is rendering-only: no gate, state-machine, or storage
behavior changes, and the explicit machine-JSON shape is frozen (see below).

Brief-by-default commands:

| Command | Brief default | Full output |
|---|---|---|
| `milestone_status` | phase, progress counts, one line per milestone (status + claim), next action | `--full` = the 7-column markdown table |
| post-mutation milestone suffix (appended after `story_advance` and every mutating command) | the compact milestone/checklist-derived summary | `PROOF_OR_STOP_BRIEF_OUTPUT=0` (or the command's own `--full`, when its schema exposes it) |
| `finding_list` | JSON skeleton: `findings[]` with `id`, `severity`, `category`, `status`, `evidenceState`, truncated `title`; `attention.suspected`/`disproven` preserved; heavy free-text (`description`, reviewer read evidence) dropped; `_brief`+`_hint` added | `--full` = every field |
| `help` | grouped command names only — every registered command listed, no per-command descriptions (with ~320 commands any in-budget description degrades into a meaningless fragment); footer pointing at `proof-or-stop <command> --help` and `proof-or-stop help --full` | `--full` = the verbose catalog (descriptions, parameter schemas, development flow) |
| `story_list` | meta fields (`_dashboard`/`_phases`/`_bugSummary`/`_testMissing`) preserved; the story array trimmed to non-terminal (actionable) stories as one-liners; per-phase counts cover ALL stories; `_brief`+`_omittedTerminal`+`_hint` added | `--full` = every story with full fields |
| `bug_list` (global, no `storyId`) | `summary` counts cover ALL bugs; the list is trimmed to open bugs; `_brief`+`_hint` added | `--full` = every bug |
| `story_review` | same JSON skeleton (round numbers, `summary`, every `issues[]` row with its `type`/`severity`); issue messages one-line, the diagnosis truncated but the `Next` remedy never (run 19; a remedy identical to an earlier issue's prints `Next: same as above.`); the multi-megabyte `_reviewPrompt` replaced by a stub naming `--full`; `_brief`+`_hint` added. CLI stdout only — the signed review.json artifact and the gate/issue computation are unchanged | `--full` = every field including the complete `_reviewPrompt` |
| `doctor` | every scan section stays visible (failing/warning rows one-line each); only the Recent-issues detail (capped truncated one-liners + omitted count) and the Validation-scan detail (counts + warnings) are trimmed; trailing brief hint | `--full` = the complete diagnostics text (`--format=json` = full machine shape) |

`validate` is deliberately excluded: `validate --full` keeps its existing
"run the real machine tests" meaning and `validate` has no brief mode.

`story_get` is audited but deliberately kept full-by-default (74KB measured on
this repo): `slim`/`fields` is its sanctioned compact opt-in, and pre-mutation
reads require the full output per the CLAUDE.md compact-status recipes
("Before evidence-sensitive conclusions or mutations, reload the full output").

`host_list` is audited and deliberately left as-is: ~16KB measured on this repo,
under the ~20KB (~5k-token) brief-by-default threshold. If host profiles grow it
past the threshold, apply the same brief pattern in a follow-up.

### Precedence: per-call flag > env > brief default

- `--full` → full output.
- `--brief` → brief output (wins over the env hatch below).
- `PROOF_OR_STOP_BRIEF_OUTPUT=0` → restores full output as the default. **Only the
  literal string `0` disables brief**; any other value (including `false`, `1`,
  or empty) keeps the brief default.
- otherwise → brief default.

### Frozen machine-JSON contract

Explicit machine JSON — `--json` or `--format=json` — always returns the current
**full** shape (same keys, same nesting) regardless of the brief settings. Brief
mode never alters the `--json`/`--format=json` field set, so machine consumers
are unaffected. Internal stdout consumers that `JSON.parse` a bare command are
also preserved in brief mode: `finding_list` keeps `findings[].evidenceState`
and `attention.suspected`; `story_list` keeps `_bugSummary`.

`story_list --active` includes INIT, INIT_CHECK, PLAN, DEV, REVIEW, TEST and
the legacy TEST_CASE / TEST_CASE_REVIEW phases. DONE, DISCARDED, IDEA and META
are excluded from this active selection. Explicit `--active` and `--phase` filters
use the resolved workspace phase before reading row details. They do not inspect
excluded Stories' checklist, bug, test-evidence or metrics details; use the
unfiltered listing for the complete dashboard and its full-population totals.
A filtered listing is not an integrity audit of excluded Stories.

### Non-silent filtering

When brief mode filters a listing to its actionable subset, it always emits the
exact total counts of the omitted items (e.g. `story_list._phases` covers every
phase, `bug_list.summary` covers every status) plus a `_hint` naming `--full`, so
nothing is hidden and `--full` recovers everything.

## Host Overflow

Proof-or-Stop Host Overflow is manual-first; Proof-or-Stop keeps story, scope,
receipt review, and merge responsibility; Claude Code is an execution host, not
a release-readiness oracle.

Use the overflow surfaces like this:

```bash
proof-or-stop dispatch_plan --storyId=B-xxxx --host=claude-code --allowedPaths=packages/main/src/foo.ts --format=json
proof-or-stop dispatch_prepare --storyId=B-xxxx --host=claude-code --allowedPaths=packages/main/src/foo.ts --format=json
proof-or-stop dispatch_run --dispatchId=D-B-xxxx-claude-code-1234 --format=json
proof-or-stop overflow_auto --storyId=B-xxxx --host=claude-code --format=json
proof-or-stop overflow_auto --storyId=B-xxxx --host=claude-code --approve=true --start=true --format=json
```

The contract is conservative by design:

- `dispatch_plan` is read-only planning. It picks a host, previews the bounded
  pack/worktree projection, and creates no dispatch record, worktree, or
  receipt.
- `dispatch_prepare` persists the bounded pack plus prompt/status placeholders
  under `.proof-or-stop/dispatches`, but it still does not create the overflow worktree
  or start a host.
- `dispatch_run` is landed. For `fake`, it runs the deterministic local harness
  and returns a local diagnostic receipt. For real hosts, it creates the
  projected isolated worktree when scaffold creation succeeds, or returns
  `failed` with a diagnostic `nextAction` when `git worktree add` cannot create
  that scaffold. It never auto-drives the external host, verifies receipts, or
  upgrades the result beyond local assurance.
- `overflow_auto` is a guarded wrapper around dispatch selection. By default it
  is suggest-only. It only materializes a dispatch when **both**
  `approve=true` and `start=true` are present; either flag by itself stays in
  suggest-only mode with an explicit warning.
- Local receipts remain diagnostic-only. Even on `accepted-local`, they do not
  become admissible gate evidence without the matching local assurance records.

### Unattended dispatch: `dispatch_auto` (policy-authorized)

`dispatch_auto` is the policy-authorized unattended scheduler. Unlike
`overflow_auto`, it may start unattended workers automatically — but only after
explicit user policy authorization and the full `dispatch_auto` launch gates
pass. The standalone `host_runtime_probe.unattendedSafe` fact remains
conservatively `false`; actual launch authorization is computed by
`dispatch_auto` from policy authorization plus Claude availability,
`claude --print` support, `commandAllowlist`, timeout/env, and scope checks. In
v1.0.1, real-host subprocess launch is Claude Code only and additionally
requires `allowRealHostSubprocess=true`; Codex and Antigravity remain
scaffolded/refused real-subprocess targets. Gemini is retained only for
deprecated legacy compatibility.

**Opt-in command sequence:**

```bash
# 1. Define or verify a dispatch policy
proof-or-stop dispatch_policy_create --policy=nightly-safe \
  --allowedHosts=fake --allowedPaths=packages/main/src/generated/ \
  --maxParallel=2 --maxRuntimeMinutes=30 --maxBudgetUSD=5.0 \
  --network=none --commandAllowlist='node -e "process.exit(0)"' \
  --allowRealHostSubprocess=false \
  --requireReceipt=true --requireReview=true \
  --allowAutoMerge=false

proof-or-stop dispatch_policy_check --policy=nightly-safe --format=json

# Claude Code real subprocess v1.0.1 requires a separate explicit opt-in policy:
# --allowedHosts=claude-code ... --allowRealHostSubprocess=true

# 2. Probe host capability (works whether or not the CLI is installed)
proof-or-stop host_runtime_probe --host=claude-code --json
proof-or-stop host_runtime_probe --host=antigravity --json

# 3. Start policy-authorized unattended workers
proof-or-stop dispatch_auto --storyId=B-xxxx --policy=nightly-safe --format=json

# 4. Watch lifecycle and runner status
proof-or-stop dispatch_watch --dispatchId=D-B-xxxx-1234 --format=json

# 5. Cancel if needed — evidence is preserved, never deleted
proof-or-stop dispatch_cancel --dispatchId=D-B-xxxx-1234 --format=json

# 6. Review transcripts, diffs, receipts, and runner evidence
proof-or-stop dispatch_review --dispatchId=D-B-xxxx-1234 --format=json

# 7. Merge manually — dispatch completion is not release readiness
proof-or-stop dispatch_merge_plan --dispatchId=D-B-xxxx-1234 --format=json
```

**`dispatch_auto` versus `overflow_auto`:**

| | `overflow_auto` | `dispatch_auto` |
|---|---|---|
| Mode | Supervised/manual-first | Policy-authorized unattended |
| Starts workers automatically | Only with `approve=true --start=true` | Yes for fake; Claude Code real subprocess only with `allowRealHostSubprocess=true` |
| Policy required | No | Yes — refuses if missing or unauthorized |
| Host safety check | No | Yes — Codex/Antigravity real subprocess support is not claimed |
| Unattended mode | No (suggest-only by default) | Yes (policy-gated) |
| Migration | Current default | Use this for unattended mode |

If you are currently using `overflow_auto` and want unattended workers, migrate
to `dispatch_auto` with an explicit policy. The `overflow_auto` `nextAction`
field will point you to `dispatch_auto` as the policy-authorized path.

**Unattended mode remains user-authorized and local-assurance-safe:**

- `host_runtime_probe.unattendedSafe` is intentionally conservative and remains
  `false`; `dispatch_auto` is the component that combines policy authorization,
  Claude availability, `claude --print` support, launcher allowlisting,
  timeout/env filtering, scope checks, and lease/conflict checks before
  starting work. Real subprocess launch in v1.0.1 is Claude Code only and
  requires `allowRealHostSubprocess=true`.
- Worker output is evidence only. `dispatch_review` surfaces transcripts, diffs,
  receipts, and runner metadata as **evidence candidates**, not as gate proof.
- `dispatch_merge_plan` is always `manualOnly=true` — dispatch completion never
  auto-merges, auto-DONEs, or widens local assurance.
- Dispatch outputs remain diagnostic until local proof-admissibility,
  receipt-bundle, and review-quorum evidence are present.

### Local Autopilot And Proof Admissibility

`autopilot_run` is the local host-to-host autopilot layer above dispatch. It
keeps the same Host Overflow boundary: hosts may execute bounded work, but
Proof-or-Stop keeps story/scope/review responsibility. Active assurance vocabulary
is `admissibilityStatus`, `assuranceLevel`, and `evidenceScope`, backed by local
gate evidence, signed/offline receipt bundles, and local review quorum.
Autopilot output does not auto-merge, auto-DONE, or widen release readiness
beyond local assurance.

Autopilot uses two policies: a dispatch policy for host/path/command execution,
and an autopilot policy for local mode permissions. The autopilot policy stores
`dispatchPolicy` as the explicit link to the underlying dispatch policy. If
`dispatchPolicy` is omitted, Proof-or-Stop falls back to the same policy name for
compatibility, but new configs should link it explicitly. Flat and nested CLI
forms are both supported:

```bash
proof-or-stop dispatch_policy_create --policy=fake-dispatch \
  --allowedHosts=fake --allowedPaths=packages/main/src/generated/ \
  --maxParallel=2 --maxRuntimeMinutes=10 --maxBudgetUSD=5 \
  --network=none --commandAllowlist='node -e "process.exit(0)"' \
  --requireReceipt=true --requireReview=true \
  --allowAutoMerge=false

proof-or-stop autopilot policy create --policy=fake \
  --dispatchPolicy=fake-dispatch \
  --mode=local --allowAutoDispatch=true --allowAutoValidate=true \
  --allowMainMerge=false \
  --maxIterations=1 --maxRuntimeMinutes=10 \
  --stopOnConflict=true --stopOnScopeViolation=true --json

proof-or-stop autopilot_policy_check --policy=fake --json
```

Run and inspect a local autopilot attempt:

```bash
proof-or-stop autopilot_run --mode=local --storyId=B-demo --policy=fake --json
proof-or-stop autopilot_status --runId=AP-B-demo-abc123 --json
proof-or-stop autopilot_watch --runId=AP-B-demo-abc123 --json
proof-or-stop autopilot_review --runId=AP-B-demo-abc123 --json
proof-or-stop autopilot_cancel --runId=AP-B-demo-abc123 --json
proof-or-stop autopilot_resume --runId=AP-B-demo-abc123 --json
proof-or-stop admissibility_waterline --storyId=B-demo --format=json
proof-or-stop quorum_submit --storyId=B-demo --runId=AP-B-demo-abc123 --hostId=codex --provider=codex --sessionId=s1 --decision=pass --materialDigest=sha256:... --json
```

`autopilot_run --mode=<mode>` is an assertion against the saved autopilot policy,
not an override. The run derives mode, retry count, runtime, budget, evidence
requirement, and dispatch policy from `.proof-or-stop/autopilot-policies/<policy>.json`
before any worker is started.

Host-native delegation is execution-only. A delegated Claude Code, Antigravity,
Codex, or fake host receives a bounded pack/prompt shape and returns transcript,
changed-file, command, and local diagnostic receipt data for review. Those local
diagnostic receipts do not establish local gate admissibility by themselves.
Local proof admissibility comes from fresh, scoped, gate-consumed evidence and
local quorum/review records, not from an active receipt server.

Merge and conflict handling stay outside autopilot. `autopilot_review` may
surface a manual merge plan, changed files, conflicts, or resume guidance, but it
must not run `git merge`, clean up the story worktree, advance DONE, or widen
local assurance. If a bounded local autopilot run hits a conflict, stale
base, denied path, missing evidence, or exhausted bound, it stops and reports the
manual next action.

Architecture and non-goals:
[`docs/requirements/decisions/host-overflow.md`](docs/requirements/decisions/host-overflow.md)

### Local Proof Admissibility

Server-backed authority modes and receipt commands are retired from the active
Proof-or-Stop CLI. The active vocabulary is:

- `admissibilityStatus`
- `assuranceLevel`
- `evidenceScope`
- gate-consumed local evidence
- local signed/offline receipt bundles
- local review quorum assurance

Use `proof-or-stop conduit status --json`, `proof-or-stop validate`, receipt-bundle smokes,
and `quorum_submit` for local assurance. Older retired decision docs are retained
only as legacy context.

The Mac App is no longer required for release or provider/config status. It is
an optional dashboard/archive surface unless a future, explicitly reviewed

### Acceptance Matrix (Wave 1)

`proof-or-stop acceptance_matrix --storyId=<id> [--json]` renders a deterministic
projection of ProofStory acceptance bindings, milestone refs, checklist and
verification-intent refs, verification-intent-owned planned-path declarations,
and existing evidence refs.

The command is observe-only, read-only, and non-evidentiary. Text output states
those boundaries explicitly; JSON contains `mode: "observe"`,
`readOnly: true`, and `evidentiary: false`. Each row exposes canonical source
IDs and stable `AT_*` structural diagnostics. A legacy binding without
`verificationTopology` reports `legacy_missing`. A configured Wave 1 graph can
report only `warning` or `inconclusive_basis_unverified`; it never reports
`complete`, `pass`, `ready-for-review`, or another authority-bearing result.

Wave 1 accepts only reference-only `proofstory.acceptance_topology.v1` data.
Existing source references are bounded to `acceptance-binding:`, `checklist:`,
`intent:`, `milestone:`, and `evidence:` owners. Planned source references name
a frozen `proofstory.verification_planned_path_declaration.v1` and endpoint ID
owned by checklist `verificationIntent`; topology cannot copy or override the
declared relation, endpoint role, file, symbol/fact, or output fact.

Only a dispatched registered verification-intent role may add a planned-path
declaration through `checklist_update` during PLAN. `story_create`,
`checklist_add`, ordinary callers, and post-PLAN mutations are rejected before
persistence. Existing verificationIntent items without declarations remain
compatible.

The renderer accepts only `storyId` and `json`. Write-shaped arguments such as
`mode`, `write`, `output`, `apply`, `result`, `verdict`, `evidence`, or `rows`
are rejected. It writes no matrix artifact, process event, evidence, phase, or
other lifecycle fact. Coverage-basis discovery, signed basis receipts, and
lifecycle enforcement are not part of the Wave 1 renderer.

Topology producer and consumer positions must resolve to declaration endpoints
with the matching canonical role. Every bound must-priority intent must be
mapped by an appropriate positive or mutation assertion, and non-docs graphs
require a command reference; omissions report stable diagnostics such as
`AT_PLANNED_PATH_DECLARATION_DRIFT`, `AT_INTENT_UNCOVERED`, and
`AT_COMMAND_MISSING`.

`acceptance_matrix` output also cannot be submitted back through
`verificationEvidence`. New matrix-derived rows are rejected before
persistence, and legacy or injected rows are ignored by general verification,
ProofStory completeness, and milestone status/closeout consumers. The shared
classifier derives provenance from an exact `acceptance_matrix` producer-command
position where possible: the supported `proof-or-stop` or `bin/proof-or-stop.js` wrapper,
optional bounded `--root`, then the exact subcommand. A token used only as `rg`
search text, `printf` data, or a test-script argument is not producer provenance.
Legacy compatibility is bounded to reserved matrix result
tokens, exact output lines, or JSON `evidentiary: false` on legacy
`manual_transcript` rows only. Paraphrased manual projection results cannot
bypass it, while logic/integration test notes may discuss those labels and
unrelated `Result: warning ...` prose is not classified as matrix output.

### Acceptance coverage basis (Wave 1A)

`proof-or-stop acceptance_basis_generate --storyId=<id> [--json]` is the sole writer
for `acceptance-basis.json`. It runs the registered PLAN discovery profile,
derives the path union and `complete | partial | unsupported` classification,
derives planned paths from frozen `verificationIntent` declarations, and signs
a receipt bound to the topology, scope artifacts, workspace identity,
`storyFilesHash`, discovered `closureFilesHash`, and the basis's structured
`snapshotSeal.sealDigest`. `snapshotSeal` records:

- `inventoryDirectoryDigest` / `inventoryDirectoryCount` for the canonical,
  bounded source-directory inventory;
- `sourceSnapshotDigest` / `sourceSnapshotCount` for safely read source files;
- `configSnapshotDigest` for the single bounded, no-follow
  `proof-or-stop.config.json` snapshot used to choose the source root;
- `status` (`complete | partial`), closed machine-coded `issues`, and the
  canonical `sealDigest` over those fields.

The signed receipt repeats `sealDigest`, so the receipt signature binds both
the complete basis (`basisDigest`) and its snapshot integrity result. The
command accepts no caller-written status, path inventory, exclusions, seal,
issuer, signature, or hash bindings. Missing/duplicate adapter results, digest
tampering, unresolved blind spots, unsupported discovery, unexplained
disagreement, an unsealable inventory, or any directory/file/config identity
or content change before the final seal cannot produce a complete basis. Such
conditions fail closed as deterministic `partial` output with structured seal
issues; arbitrary free-text blind spots are not accepted as seal evidence.

`proof-or-stop acceptance_basis --storyId=<id> [--json]` is read-only. It recomputes
the current canonical discovery and physical snapshot seal, then verifies the
stored structured seal, `sealDigest`, `basisDigest`, signed receipt binding,
and expected current seal/semantic digest. A source/config change or a newly
added consumer after receipt issuance therefore makes the read invalid rather
than reusing the old complete claim. A legacy Story without the artifact
reports `legacy_missing`; an authentic partial basis remains explicitly
`partial`, while stale or tampered artifacts report deterministic `AT_*`
diagnostics.

Wave 2 promotes the verifier-produced basis to an L4 gate-consumed process fact
for PLAN→DEV structural evaluation. The basis commands themselves remain
non-Authority: they do not advance lifecycle state, accept caller verdicts, or
prove executable readiness.

### Acceptance topology structural check (Wave 2)

`proof-or-stop acceptance_topology_check --storyId=<id> [--json]` is the canonical
read-only PLAN structural evaluator. It loads the stored verifier-signed basis,
re-derives current discovery and workspace/scope/topology bindings, verifies the
receipt, and compares the complete basis union with the normalized reference-
only topology. Text and JSON both report `mode`, `status`, `basisStatus`,
`structuralPass`, `blocking`, ordered `diagnostics`, and an exact `nextAction`.
JSON additionally states `readOnly: true`, `evidentiary: false`, and
`authority: "diagnostic_only"`.

Mode comes only from the independent flat project
`proofStory.acceptanceTopologyGateMode` setting. It defaults to `observe` even
when the older ProofStory `devGateMode` is `enforce`, so shipping Wave 2 does
not silently enable its project-wide rollout:

- all three modes return the same `status`, `structuralPass`, and ordered
  `AT_*` diagnostics;
- `observe` and `warn` do not block PLAN→DEV;
- `enforce` blocks PLAN→DEV when that same canonical result is non-pass;
- rollback from `enforce` to `warn` changes admission only and does not rewrite
  the basis, topology, diagnostics, evidence, or prior history.

The command accepts only `storyId` and `json`. Caller fields such as `mode`,
`status`, `structuralPass`, `blocking`, `authority`, `basis`, `evidence`,
`write`, or `apply` are rejected. Missing basis/topology, partial or unsupported
basis, stale/tampered receipt or adapter projection, an unmapped basis path,
topology invention outside the basis, invalid typed planned paths, orphan refs,
and uncovered required intents produce stable ordered `AT_*` diagnostics.
Partial/unsupported/missing basis is explicitly inconclusive, never a pass.

PLAN compatibility is structural: documentation-only and ordinary single-
outcome bindings do not fabricate runtime mutation/transcript requirements;
legacy missing topology remains readable and visible as `AT_MISSING_TOPOLOGY`.
A new producer→consumer path may enter DEV only through a frozen typed planned-
path declaration owned by `verificationIntent` and independently derived into
the PLAN basis. The check does not run commands, consume `verificationEvidence`,
require an implementation transcript, persist a result, or claim executable or
production readiness. Independent critic, current-worktree executable checks,
selective per-Story policy, and measured rollout remain later bounded waves.

### Independent topology critic (Wave 2A)

Wave 2A adds a mechanically attributable review layer over the structural
topology result. `proof-or-stop topology_critic_receipt_set --storyId=<id>
--verdict=pass|request_changes` is the sole producer for the signed
`topology-critic-receipt.json`; `proof-or-stop topology_critic_receipt_check
--storyId=<id> [--json]` is its read-only verifier. The producer is restricted
to a dispatched `proof-or-stop-review-topology-critic` identity and the verifier
recomputes all current bindings instead of trusting caller-supplied hashes or
status fields.

The receipt binds the current basis and topology digests, scope-check and
optional scope-contract digests, `storyFilesHash`, `closureFilesHash`, finding
refs, exclusion-approval refs, critic provenance, implementation provenance,
verdict, signer key, and issuance time. It passes only when the critic differs
from the implementation provenance in all four dimensions: agent identity,
session identity, dispatch identity, and business-commit author identity.
Role labels in prose are not evidence.

When the basis contains an exclusion, `proof-or-stop
topology_exclusion_approval_set --storyId=<id> --exclusionRef=<decision-ref>`
creates an independently signed approval from the registered
`proof-or-stop-review-scope-plan` role. Approvals must form an exact one-to-one map
to the current exclusions and remain independent of both implementation and
critic provenance. Missing, duplicate, forged, stale, orphaned, or cross-Story
approvals fail verification.

Neither a critic verdict nor an exclusion approval can convert a `partial` or
`unsupported` discovery basis into a pass. Wave 2A does not add executable
`pre_review_check`, selective applicability, enforcement rollout, or telemetry.
The receipt has no lifecycle admission consumer in Wave 2A: its absence or
failure cannot block PLAN → DEV. Wave 3 owns `pre_review_check` enforcement;
selective applicability and rollout remain Wave 3A and Wave 4 responsibilities.

### Executable pre-review check (Wave 3)

`proof-or-stop pre_review_check --storyId=<id> [--json]` is the sole writer for the
signed `pre-review-check.json`. It recomputes a `phaseBasis=pre_review` basis
from the current worktree, binds the prior PLAN basis digest, reconciles every
frozen planned path to current producer/consumer symbols, and derives ordered
`PR_*` results from current hash-bound verification evidence. Passing evidence
must predate the verifier cutoff; evidence at or after the cutoff is excluded.
The artifact binds topology/scope/story/closure hashes, evidence digests, flat
project mode, cutoff, and (in enforce mode) the current independent topology-
critic re-attestation.

`proof-or-stop pre_review_check_read --storyId=<id> [--json]` is read-only and calls
the same production verifier used by DEV→REVIEW. `observe` and `warn` preserve
diagnostics without blocking; `enforce` blocks DEV→REVIEW on the same result.
Neither command accepts caller-authored verdict, authority, mode, hashes,
evidence, timestamps, or signatures. Wave 3 does not add per-Story selective
applicability (Wave 3A) or measured rollout/telemetry (Wave 4).

### Evidence-chain check (framework-owned, never a review finding)

Review findings must be real product defects. Evidence-chain problems are
detected mechanically before REVIEW by `core/evidence-chain-check.ts`
(wired in `handlers/evidence-chain.ts`) and each report names exactly one
`Next:` command. The text output of `pre_review_check` and
`pre_review_check_read` ends with an `Evidence-chain check` section, and the
DEV→REVIEW transition runs the same check (after `pre_review_check` and the
acceptance rollout gate, before the canonical REVIEW evidence gate):

| Item | Blocks DEV→REVIEW | Next |
|---|---|---|
| `stale_receipt`: a must/should intent's receipt is stale | yes | `proof-or-stop verification_evidence_refresh_stale --storyId=<id>` (reruns every stale pinned command once); when a pinned must intent is also missing, the stale pinned rows join that `verification_run --pending` batch instead |
| `missing_receipt`: an executable must/should intent has no admissible receipt | must: yes; should: advisory | pinned must intent: one `proof-or-stop verification_run '{"storyId":"<id>","pending":true}'` for all of them (see below); pinned should intent: `verification_run --intentRef`; unpinned (PLAN normally pins them, see "PLAN pins" below): ONE `verification_evidence_batch_add` template for every unpinned missing intent whose `command`, `selector` and `note` are `<...>` placeholders the agent authors, plus ranked candidate tests per intent |
| `unbound_test`: a Go `func TestX(t *testing.T)` added/changed in the Story diff that no pinned `go test` selects | advisory | a `verification_evidence_add` template with this test's command and the item's unpinned intents listed in a placeholder `intentRef`: bind it only to the intent it proves; when every intent is already pinned, no action unless it is the only test of a userSees behavior (`acceptance_amendment_propose`) |

**Which test proves which intent is a judgment, never mechanics** (run 16). The
check never chooses a test for an unpinned intent. Before, it proposed the first
changed Go test of any file of the item, wrote the note "X proves: <desc>" itself
and `next` labelled it `framework`, so `next --run` would have pinned
`TestParsingIndexRangeExpressions` (two-part ranges only) for
`myArray[99 : 101 : 2]`, immutably, with a passing receipt. Now each unpinned
missing intent lists up to 4 candidates (changed tests of the item no pin
selects) with their exact `go test -v ./pkg -run ^TestX$` command and why:
code-like literals of the intent description (bracket and paren expressions,
quoted and backticked strings, compared without whitespace and escapes) found in
the test body rank first, then words the test name shares with the description;
a candidate without a literal says so. The gate refusal and `pre_review_check`
print them in the item's detail. No report text ever states that a test proves
an intent.

**`verification_run --pending` (batch).** It covers every pinned must/should
intent whose receipt is stale and every pinned must intent whose receipt is
missing or non-mechanical (`pendingPinnedVerificationIntents`, the same
selection the chain uses). Each unique pinned execution (command, cwd,
timeout and execution identity, at the current HEAD/material) runs once. Every
intent pinned to it gets its own signed assertion receipt from the same
enforcement boundary as single `verification_run`, judged by its own selector
against the complete shared output. All passing rows are written in one
checklist write with one metadata commit. Refusals stay per intent. A selector
absent from the shared output refuses only that intent; its completed execution
is still shared with the other intents of its key. A non-zero exit or timeout
refuses every intent of that execution without relaunching it. No row is minted
for a refused intent, and the command exits non-zero naming each one. Any other
error (identity drift, preflight refusal) writes nothing. Run 14 needed 49
`verification_run` steps (one per intent, 10 unique commands, 49 metadata
commits, 16.8 min). The regression smoke
`packages/main/dist/tasks/verification-batch-dedupe-smoke.js` has 6 intents
over 2 commands: 6 steps / 6 launches / 6 commits / 18.2 s before, 1 step /
2 launches / 1 commit / 7–8 s after.

Each receipt binds the exact pinned command it executed: every consumer
(gate admissibility, `pre_review_check`, the inventory observation, narrowing,
intent fingerprints, publication recovery) requires
`executionReceipt.command === pin.command` and derives the execution identity
from the pinned command. Distinct pinned commands are therefore never merged
into one `go test -run '^(A|B)$'` run: that run is a different command, a
different execution identity, and a different process (the tests of the
package share one binary, its globals and its order), so its output is not a
receipt for any single pin (run 17 Q2, lab verify-batch-and-gate-dupes). What
the batch saves is the work around each launch: the validation reservation
controller observes its own process identity and the machine boot session
once per process (it ran 5 `ps` and 1 `sysctl` per execution), and the
Story-diff memo is no longer disabled by `GIT_EDITOR` (3–4 `git diff` per
execution). Per pinned execution the batch now starts ~6 child processes
besides the pinned command (HEAD and status before and after it, the child's
identity, the process table), 16.7 → 8.0 amortized at 22 pins
(`packages/main/dist/tasks/verify-batch-and-gate-dupes-smoke.js`).
`verification_evidence_refresh_stale` shares the same executor and savings.

**PLAN pins.** `story_review` blocks (`missing_verification_pin`, one row per
item, naming the refs) every executable (`logic`/`cli`/`browser`) must/should
intent without `verification:{command,selector}`; manual/docs and nice intents
are exempt. The owner pins them with `checklist_update` in PLAN (the test may
not exist yet; the implementer prompt lists the pins and requires exactly these
test names). Pins freeze at DEV, so `verification_run --pending` then records
every receipt in one call. Paths that skip `story_review` (express channel,
light profile) can still reach DEV unpinned; there the batch template above
applies. Run 16 had no pins: 32 receipts were hand-authored with single
`verification_evidence_add` calls (5.3 min, 15 shell-quoting failures).

Selection is computed, never guessed: `go test [pkgs] -run/-skip` with
unanchored RE2-style top-level matching, `./...`, `./dir`, and module import
paths. A pinned command whose selection is not computable (make, a shell, a
foreign import path, a file list, a regex JS cannot express) skips the scan and
prints `unboundTests=skipped: <reason>`. JS/TS test selection is not scanned.
The check defers to the checklist gate while items are open and fails open on
its own errors.

A reviewer that still reports an evidence-chain item uses
`category: "evidence_chain"`. `managed_review_evidence_import` imports only the
product findings (bound to their sealed proposal indexes); a proposal with only
evidence-chain items is imported as a pass whose note the verifier recomputes
from the sealed proposal. Each item is logged as a
`review_evidence_chain_reclassified` process event and the import prints
`Framework next action: <command>`. Native `finding_add` refuses the category
(`evidence_chain_not_a_finding`) with the same next action. An inventory
critic proposal may not carry such items.

A managed inventory critic's `inventoryCritic.findingDispositions` needs exactly
one row for every VERIFIED aggregate finding of the wave (by `findingId`), no
row for a suspected or disproven finding, and one row for every entry of its
own `findings` (by `proposalFindingIndex`); the protocol prompt
(`MANAGED_INVENTORY_CRITIC_PROTOCOL`), the schema descriptions and the evidence
pack (the exact id lists) say so, and say that its own findings are only for
defects no aggregate finding already reports. The same id lists are sealed in
the run's `reviewBinding.inventoryCriticCoverage` (computed with the importer's
wave evaluation at `host_run`); before sealing, the worker checks the block
against them (`managedInventoryCriticCoverageViolations`) and a missing row is
a same-session format repair naming the exact ids
(`managed_review_final_result_malformed:inventory_critic_coverage`), not a
sealed block the importer refuses and not a fresh critic. A row for an id
outside the verified set (run 19, B-8166: a `verified_family` row for suspected
F-001, refused `REVIEW_INVENTORY_FINDING_DISPOSITION_INVALID`, after which the
owner relaunched the critic and finally wrote an empty receipt itself) carries
no authority: the importer drops it and logs process event
`inventory_critic_disposition_dropped` instead of refusing the critic; rows for
in-set findings are never dropped, and completeness is computed over the
in-set findings only. A critic cannot promote a suspected finding to verified
this way (that would change detection; left to the A/B). The receipt of a
managed critic run is written only by `managed_review_evidence_import` from its
sealed block: `review_inventory_critic_set` for a ReviewRun with managed
terminal evidence refuses `REVIEW_INVENTORY_CRITIC_MANAGED_RECEIPT_ONLY`
(`Next: proof-or-stop next --storyId=<id>`), and `review_inventory_status`
proposes `next` instead of a critic_set for such a run.
At import, a missing row still refuses the critic receipt with
`REVIEW_INVENTORY_FINDING_DISPOSITION_INCOMPLETE: <ids>` (the terminal evidence
stays imported). One exception is completed by the importer instead of
refused (and is therefore not a worker repair either): a critic finding that provably restates an earlier finding of the
wave (at least one shared cited file and the same claim: token Jaccard
similarity >= 0.6 with a 0.15 margin over the runner-up and no disjoint code
symbols, i.e. when both name functions/identifiers they share one; or >= 0.25
when the critic's own row names that finding's id), where only one of the two copies has
a row. The other copy is recorded as a `duplicate` of the canonical finding
(the critic's row for the lane finding is kept; when the critic wrote its row
on its own restatement, that row moves to the lane finding and the restatement
becomes the duplicate). The restated copy stays a verified finding and closes
through the duplicate-coverage path; a new, ambiguous or unrelated critic
finding is never reconciled away (`reconcileRestatedCriticFindings`,
core/managed-inventory-critic.ts; detection A/B control D2-r3, D9-r1). A refused
critic import is recorded as process event `inventory_critic_import_refused`,
and `next` then runs a fresh critic of the same wave instead of the same import.
The same holds when the import of any managed review receipt (lane or critic) is
refused BEFORE any evidence was persisted for a reason no retry can change
(`isDeterministicManagedImportRefusal`: candidate routing rejected, no admissible
provider proposal, invalid critic purpose/wave, an evidence_chain item in a critic
proposal, or a live-binding refusal that says to rerun the reviewer): the refusal
is recorded once as process event `managed_review_import_refused` for that exact
run/receipt, `next` never proposes that import again (alone or in a batch), and
relaunches instead: a fresh critic of the same wave (its prompt names the
refusal), or for a lane, `review_round_prepare` starts a fresh run of it
(`refusedManagedReviewImport`, handlers/managed-review-evidence.ts). Transient
refusals (staged metadata, unreadable status) are retried. A/B V3 R2A-r2
(de80753) looped on such a refusal: the round-2 critic read
`candidate-spec-set.json` (artifactDigest `ba5faa35…`) and wrote a different
64-hex value (`8577ba20…`) into `readManifest.candidateSpecSetDigest`; the route
had not changed. The candidate route a managed reviewer is launched against is
now sealed in its run spec (`reviewBinding.candidateRouting`:
`candidateSpecSetDigest` + `corpusDigest`), and the worker seals the proposal
with those controller-owned values instead of the provider's transcription
(`withSealedCandidateRouting`, journaled as run event
`read_manifest_routing_sealed` with both values), as it already does for the
full-scan reason. A route that really changed after launch still refuses at
import (sealed launch digest != current artifact) and takes the relaunch path above.
That fresh critic does not make the earlier critic's findings stale (the
`stale_run` rule exempts inventory-completeness critic runs of the same epoch
wave, core/review-run.ts); the fresh critic classifies them by `findingId`.

### Acceptance rollout report and admission check (Wave 4)

`proof-or-stop acceptance_rollout_report --storyId=<id> [--json]` runs the registered
`runProofStoryAcceptanceRolloutCohort` producer over real temporary Story
artifact trees and is the sole writer of signed
`acceptance-rollout-report.json`. Membership is verifier-derived and frozen
from every eligible comparable record in the declared window. The caller
cannot provide the window, membership, source rows, thresholds, aggregates,
verdict, adapter, provider, quorum, hashes, receipt, or signature.

`proof-or-stop acceptance_rollout_report_read --storyId=<id> [--json]` verifies the
stored signature, report/source/membership digests, current
`headHash`/`materialHash`/`storyFilesHash`, registered runner digest, threshold
verdict, supported adapter profile, and genuine full 3 rounds × 2 hosts.

`proof-or-stop acceptance_rollout_check --storyId=<id> [--json]` is the canonical
flat-project policy projection consumed by DEV→REVIEW. Promotion requires:

- at least three matched baseline/candidate pairs in each arm;
- every registered seeded defect detected and overall false-pass count `0`;
- supported omission detection `100%` and false-block rate `0%`;
- mislabeled degraded 3×1 count `0`;
- waiver delta `<= 0` and non-shrinking check inventory;
- transcripts for user-visible/orchestration claims and biting mutations for
  behavior/lifecycle/proof/safety claims (docs-only is exempt);
- only the registered `codex-cli+claude-cli` adapter profile and genuine
  `full-3x2` quorum.

Mode comes only from flat project
`proofStory.acceptanceRolloutGateMode` (`observe` by default). Observe, warn,
and enforce return the same status, receipt classification, threshold result,
and ordered `AR_*` diagnostics. Observe/warn remain non-blocking; enforce alone
blocks DEV→REVIEW. Rollback sets that config to `warn` or `observe`; it never
deletes or rewrites reports, receipts, failed attempts, diagnostics, or prior
evidence. Wave 3A selective per-Story applicability remains unimplemented and
excluded. The report is local assurance, not release, production, or public
Authority evidence.

### Milestone Status

`proof-or-stop milestone_status` is a read-only progress reporter over existing
ProofStory facts. For active and other non-DONE stories, it is a live
projection: it reads the current story phase, milestone ledger state/hash,
checklist refs, verificationIntent refs, verificationEvidence, and optional
summary facts. It does not create milestone storage.

For DONE stories, `milestone_status` first looks for a schema-valid
`.proof-or-stop/story/actives/<storyId>/milestone-closeout.json`. When that closeout
snapshot exists, the command renders the normal Milestone Status table from the
frozen closeout-backed status report instead of recomputing live evidence
freshness after active worktree cleanup. If a DONE story has no valid closeout
snapshot, the command falls back to the live projection and missing or stale
live evidence remains blocked; it does not fabricate a completed result.

```bash
proof-or-stop milestone_status --storyId=B-xxxx
proof-or-stop milestone_status --storyId=B-xxxx --format=json
proof-or-stop milestone_status --storyId=B-xxxx --json
```

The command accepts only `storyId`, `format`, `json`, `full`, and `brief`. Every
other key is rejected before story facts are read.

Text output is **brief by default** (phase, progress counts, one line per
milestone, and the next action — see
[Brief-by-default outputs](#brief-by-default-outputs-agent-loop-context-hygiene)).
With `--full` (or `PROOF_OR_STOP_BRIEF_OUTPUT=0`) text output includes the grouped
Markdown tables for completed, current, and remaining milestones. JSON output is
always a `MilestoneStatusReport`-shaped
object with `storyId`, `phase`, `ledger`, `mode`, `milestones`, `groups`,
`risks`, and `nextActions`; DONE closeout-backed JSON uses the same shape and
preserves the frozen closeout groups and ledger summary. `mode.readOnly` is
`true`; `runCommands`, `writeEvidence`, `advancePhase`, and `launchReviewers`
are always `false`.

Host Progress Reporting Contract:

- Hosts should print or attach the full `milestone_status` table after a
  milestone or sub-objective status change, at handoff, and before final
  responses when milestone progress is relevant.
- The CLI automatically appends the consumed `milestone_status` summary after
  successful human-text output for the configured story-scoped mutating
  commands that update milestone ledgers, checklist state, verification
  evidence, story phase, delivery checks, or summaries. This appended suffix is
  **brief by default**; `PROOF_OR_STOP_BRIEF_OUTPUT=0` restores the full Markdown table
  (per-call `--full` on a mutating command is honored only when that command's
  own schema exposes it).
- Developer-facing milestone tables render real row status cells with six text
  labels: `✅ Done` for final completed ledger/sub-objective/evidence pass or
  coverage, `⏳ In Progress` for the active milestone/checklist/running work,
  `🟡 Pending Review` when evidence is covered or implementation appears
  complete but ledger/review/final acceptance is not done yet, `⬜ Not Started`
  for remaining future work and pending checklist/intent before active work,
  `🔴 Blocked` for missing ledgers, missing refs, unmapped or ambiguous intent,
  stale evidence, or missing required evidence that blocks progress, and
  `❌ Failed` only for failing/not-passing evidence or explicit failed status.
  Real sub-objective and evidence rows use the same icon plus short label before
  their ids. Empty placeholder `none` rows stay unmarked for readability and
  deterministic table output. `❌` means Failed; it must not be used for Not
  Started rows.
- Automatic append is skipped for `--json` / `--format=json` so machine stdout
  remains parseable. For human-text mutation output, a story with
  `milestone-ledger.json` appends the `Milestone Status - <id>` summary (brief by
  default, full table under `PROOF_OR_STOP_BRIEF_OUTPUT=0`); a story without a ledger
  appends a distinct `Checklist-derived ledger (no milestone ledger set) - <id>`
  status block (also brief by default).
- Missing `milestone-ledger.json` is a blocker in the live projection. The
  checklist-derived block is display-only fallback status: it reports a clear
  next action and does not infer completion from checklist text alone. A DONE
  closeout-backed report uses the ledger summary already frozen in the closeout
  snapshot.
- Detail granularity comes from the authored milestone ledger, checklist refs,
  verificationIntent refs, and verificationEvidence. Future completion or
  executor ledgers can improve state-change deltas, but V1 does not require them
  and reports only current committed story facts.
- `requiredEvidence` entries that match supported verification evidence kinds
  (`logic_test`, `integration_test`, `browser_test`, `manual_transcript`,
  `docs_check`, or `waiver`) are enforced against fresh covering evidence of
  that exact kind. Historical custom labels are displayed as mapped hints, not
  evidence-kind gates. Passing evidence and permanent non-failing waivers can
  cover verification refs; deferred gate-evidence waivers and failed waivers do
  not.
- Evidence freshness prefers the strongest comparable story-scoped binding:
  matching `storyFilesHash` is authoritative when both the current workspace and
  the evidence provide it, so metadata-only `materialHash` drift does not block
  progress reporting. The empty story-files hash is treated as no story-scoped
  signal, not as freshness proof. If no comparable non-empty `storyFilesHash`
  exists, comparable `materialHash` is checked. `headHash` is a hard fallback
  only for legacy or degraded bindings that lack those stronger hashes, so
  metadata-only HEAD movement does not block completion by itself.
- V1 is read-only. It rejects mutation-like flags such as `runCommands`,
  `writeEvidence`, `advancePhase`, `launchReviewers`, `write`, `apply`,
  `execute`, `run`, `launch`, `capture`, `refresh`, and flags that claim local
  completion or claim remote Authority completion before reading story facts.
- V1 does not run commands, write evidence or summaries, write review passes,
  change phase, launch reviewers, claim automatic execution, claim automatic
  DONE, claim remote Authority completion, or claim production readiness.

### Milestone Closeout

`proof-or-stop milestone_closeout` is the read-only historical DONE closeout reader.
It reads `.proof-or-stop/story/actives/<storyId>/milestone-closeout.json`, a snapshot
captured during DONE advancement from a completed, risk-free live
`milestone_status` report. It does not recompute current freshness; DONE
`milestone_status` uses the same frozen snapshot, when present, to render the
normal grouped status table after active cleanup.

```bash
proof-or-stop milestone_closeout --storyId=B-xxxx
proof-or-stop milestone_closeout --storyId=B-xxxx --format=json
proof-or-stop milestone_closeout --storyId=B-xxxx --json
```

The command accepts only `storyId`, `format`, and `json`. Mutation-like flags are
rejected before story facts are read. Text output uses the closeout columns
`Milestone`, `Status`, `Solved Problem`, `Acceptance`, `Evidence`, `Risks`, and
`Next Action`.

Snapshot creation is stricter than display: the DONE path skips capture when no
milestone ledger exists, but if a ledger exists the closeout write must come from
a report with every row completed and no risks. Incomplete or risk-bearing
milestone reports block rather than writing a false closeout. When the snapshot
is written from a story worktree DONE path, it is committed with the story
metadata before the worktree is removed, so the canonical main root can still
read it after merge cleanup. When the snapshot is missing, `milestone_closeout`
prints a diagnostic and a next action; `milestone_status` then remains a live
readiness projection and missing or stale evidence is still reported as such.

### Autopilot (local)

`proof-or-stop autopilot ...` exposes a bounded unattended-development control plane.
It is local-only in the active CLI and uses the same local lifecycle gates,
proof admissibility, receipt-bundle, and quorum evidence as ordinary work.

```bash
proof-or-stop autopilot status --json
proof-or-stop autopilot doctor --json
proof-or-stop autopilot run --mode=local --storyId=B-xxxx --until=TEST --json
proof-or-stop autopilot execute --mode=local --storyId=B-xxxx --until=TEST --maxSteps=20 --json
```

Mode contract:

- `local` is the only active mode. It plans the ordinary local Proof-or-Stop workflow
  (`session_brief`, `aux_doc_list`, story inspection, `validate`, `check`, and
  optional `codex verify`).

`autopilot_run` is dry-run by default. A default invocation only returns a plan
and is treated as read-only by the command policy. Passing `--dryRun=false` may
append a story-scoped `autopilot_projection` process event, but that event is
not lifecycle gate evidence, does not execute providers, and cannot widen local
assurance.

`autopilot_execute` is the true bounded executor loop. It requires `--storyId`
for non-dry-run execution, runs only argv-mapped Proof-or-Stop commands, appends a
non-authoritative `autopilot_execution` event, and can optionally invoke Claude
Code CLI repair with `--allowClaudeRepair=true`. The repair hook is disabled by
default and every repaired step is re-run before the executor continues.

Regression coverage is local autopilot execution plus proof-admissibility and
receipt-bundle smokes.

### Planner (natural language → Story + plan)

`proof-or-stop planner ...` is the Proof-or-Stop-native planner surface. It turns a
natural-language request into a Proof-or-Stop Story draft, checklist, verification
intent, and typed `plannedSteps[]` that the autopilot executor can run. It does
not hand Story, job, or receipt authority to any external framework.

```bash
proof-or-stop planner draft --request="Add a hello command that prints hi" --json
proof-or-stop planner review --draftFile=draft.json --json
proof-or-stop planner status --runId=<plannerRun> --json
proof-or-stop planner source-manifest --sourceRepo=<path> --json
proof-or-stop planner run --request="<one sentence>" --mode=local --until=DONE --json
```

Boundaries:

- `planner draft`, `planner review`, `planner status`, and
  `planner source-manifest` are read-only. `planner create-story` /
  `planner create-job` mutate only through Proof-or-Stop commands.
- Interaction mode is `--interactionMode=autonomous|interview|decision-gated`
  (default `autonomous`); paused runs use `planner answer` /
  `planner decision submit` / `planner resume`.
- `planner run` composes draft → review → Story → local plan → executor, but
  DONE still obeys the same local gates as autopilot. Treat it as the planning
  entrypoint, not a guarantee of unattended DONE.

### Source-Aligned Redevelopment Workflow

`planner run --workflow=source-aligned-redevelopment` composes a source-aligned
redevelopment plan: take an authorized source codebase and reproduce its
modules, functions, behavior, and fine details in a target project and target
language, with project-name-based identifier renaming.

```bash
proof-or-stop planner run --workflow=source-aligned-redevelopment \
  --sourceRepo=<path-or-ref> --targetProject=<path> --targetProjectName=<name> \
  --sourceLanguage=typescript --targetLanguage=rust \
  --mode=local --until=DONE --json
```

Boundaries:

- It is a development workflow, not a new interaction mode; it runs under
  `autonomous` / `interview` / `decision-gated` and under local Proof-or-Stop gates.
- The source codebase is read-only input; target files are written only through
  the story worktree and normal lifecycle gates. The workflow is language-pair
  agnostic (e.g. `typescript -> rust`, `swift -> kotlin`).
- It preserves license/attribution notices and excludes secrets, `.git`, caches,
  and build outputs from prompts/output/evidence. It produces evidence-backed
  alignment, not a promise of perfect semantic identity; unverifiable in-scope
  details are recorded as explicit gaps. This is a current-pass capability gated
  on its fixtures, not part of the already-shipped baseline.

## Proof-or-Stop State Entry Point

Proof-or-Stop is not responsible for the Codex / Claude Code agent runtime; it is responsible for project state: story, phase, worktree, gate, review, fixture, bug, and evidence.

When restoring context, prefer the read-only entry points:

```bash
proof-or-stop status
proof-or-stop next
```

- `proof-or-stop status` shows an overview of the current project state, reusing `session_brief`'s source of truth
- `proof-or-stop next` outputs only the single most reliable next-step suggestion
- Neither command advances the phase, writes `.proof-or-stop/state`, or modifies story/fixture/git

### `next --storyId`: the framework drives INIT → DONE

From `story_create` on the owner does not work out the INIT_CHECK entry, the DEV
entry or the REVIEW → PRE_CERT → TEST → DONE ceremony (lab
`owner-init-and-worker-prompt`, N4: in old-PoS runs 22–24 the owner spent 30–36 of
62–97 requests in INIT on `--help` pages, manual INIT reviewer launches and polls,
and boundary / freeze / preflight commands one at a time).

```bash
proof-or-stop next                           # no unfinished Story: the one story_create template (step story_create_authoring)
proof-or-stop next --storyId=B-xxxx          # one step, human-readable; last line is `Next: <command>`
proof-or-stop next --storyId=B-xxxx --json   # the same step as JSON
proof-or-stop next --storyId=B-xxxx --run    # run framework steps, bound launches and waits (one 285 s wait budget by default), stop at the next agent step
```

With no unfinished Story, `next` (no `--storyId`) returns the agent step
`story_create_authoring`: ONE complete `story_create` command whose payload has
every authored value as a `<...>` placeholder with a one-line hint (name, title,
description, type, priority, keywords, the four-section background with its
length rule, one checklist item with `files` and one classified, pinned happy
intent row with a `derivation` placeholder to copy per deliverable (kept on an
expected output `request.md` does not quote, dropped on a quoted one; see the
derivation rule below), and `scopeBoundary` / `executionBoundary`
inline, the execution boundary prefilled with the project's validate commands,
`git` and `proof-or-stop`). A staged request is recorded by `story_create` itself.
With unfinished Stories it keeps the session projection. `story_create` then ends
with `Next: proof-or-stop next --storyId=<id> --run`.

INIT and INIT_CHECK are decided from the INIT_CHECK gate's own failure
(`getGuardFailureReason(INIT_CHECK)`, in the order the gate checks): the
boundaries, the deterministic `scope_freeze_check` (the core evaluates it; the
caller only records it, so it is a framework step), then the two required INIT
reviewers (`proof-or-stop-review-story-init`, `proof-or-stop-product-reviewer`),
both launched before the first wait so they run in parallel; then
`story_advance INIT_CHECK` (creates the Story worktree) and `story_advance PLAN`.
A Story with a worktree is decided and run from that worktree: called from
anywhere else (the main checkout right after INIT_CHECK), `next` runs the same
call in the worktree, prints `Story worktree: <path> ... cd <path>`, and the
JSON carries `worktree`. Inside one `next --run` the loop continues in the
worktree with the budget left.

It is read-only (no metadata, evidence, audit event or commit is written) and
returns exactly one step:

| Field | Meaning |
|---|---|
| `phase` | the Story phase the step was decided from |
| `kind` | `framework`: a mechanical step the framework runs itself under `--run` (gate steps, waits, and fully bound managed launches); `agent`: needs the agent (a launch whose selection is not yet bound or that replaces a failed run, a `<...>` value to author: summary / decision / resolution / live-smoke command, a host verdict); `human`: a genuine human decision (stall resume, approval, 3x2 quorum) |
| `reason` | stable step code, e.g. `review_lane_launch`, `precert_cheap_check` |
| `command` / `argv` / `cli` | the exact call (ids, run ids, receipt ids and digests filled in) as a shell line, as `['proof-or-stop', <command>, <JSON payload>]`, and as `{command, payload}` |
| `placeholders` | payload paths the agent must author (their values are `<...>`), nested ones as `evidences[0].command`; nothing else is to be changed. A step with placeholders is always `agent`, never `framework`, so `--run` never executes a `<...>` value |
| `placeholderHints` | one line per placeholder describing its expected content (curated for `finding_resolve`, `summary_set`, `dev_memory_finish_decision`, `dev_memory_capture`, `live_smoke_transcript`, `decision_set`, `plan_set`; otherwise the `<...>` text itself), printed under `Author before running`, so no `--help` read is needed |
| `launch` | a managed `host_run` that needs no judgment: host/model/effort are this Story's own earlier selection (all three set), the payload has no placeholder, and no earlier run of the same target exists (lane/critic: no earlier non-completed run of the lane in the round; implementer: of the item; finding repair: of the finding; delivery: since TEST entry; scope-plan: none, or for a stale verdict the last run completed and delivered it, `scopePlanLaunchIsFramework`) or every earlier run of a lane, critic, item, finding or scope-plan target failed auto-replaceably (supervisor never ready; `provider_stalled` or `provider_transport_error` with no work product; a managed review run that ended with no valid final envelope after the same-session format repair, `managed_review_final_result_*`; docs/host-run-usage.md), at most 3 (`targetRelaunchIsFramework`). Kind `framework`; `--run` launches it |
| `parallel` | independent fully bound launches run concurrently in ONE step, each its own process with exactly the command it would have alone (`review_lane_launch`: every prepared lane of the round; v4.1 cost plan N2). `command`/`argv`/`cli` hold the first; `--run` spawns them all at once and waits for all; an agent runs every listed command before the next `next` |
| `batch` / `optional` | several authoring commands for ONE agent turn, each with its exact command and placeholder hints (`test_authoring`: `dev_memory_finish_decision` + `summary_set`; `plan_authoring`: before the scope-plan reviewer one `checklist_update` per item, after it `decision_set` / `plan_set` + `story_review`); `optional` lists a command that may come first (`dev_memory_capture` before `decision=captured`) |
| `why` / `source` | why this is the step, and which gate predicate or reader decided it |
| `wait` / `done` | a blocking wait on a detached managed run / the Story is DONE |

A wait step (`wait: true`, reason `managed_run_wait`) renders with the owner
wait instruction as its first line:
`Wait: this call blocks up to 285 s; give it a tool yield/shell timeout of 300000 ms (Codex: yield_time_ms=300000; Codex returns exec_command after 30 s while it still runs, whatever the yield: then call write_stdin yield_time_ms=300000 on the same session once, with empty input). Do not poll more often; ...`.
Its command is the compact text `host_run_status --untilTerminal=true`, which
blocks server-side up to 285 s (inside one 300000 ms yield and under the CLI's
5-minute idle watchdog).

Codex note (v4.1 cost plan N5, old-PoS runs 22-24): Codex 0.154 returns every
`exec_command` after 30.0 s while the command still runs, whatever
`yield_time_ms` asks; only the `write_stdin` poll on the same session honours a
long yield, bounded by Codex's `background_terminal_max_timeout` (default
300000). The owners already passed `yield_time_ms=300000`: 34 of 34 `next --run`
calls that blocked longer than 30 s returned at exactly 30.0 s (11 / 8 / 15 in
runs 22 / 23 / 24), streamed output or none. So on Codex a blocking call longer
than 30 s always costs two owner turns (exec, one poll); streaming cannot avoid
it. What PoS controls is how much one pair covers: the server-side block is
`PROOF_OR_STOP_OWNER_WAIT_BLOCK_MS` (30000-585000, default 285000; the
until-terminal status wait caps at 600 s) and every wait instruction names the
matching yield (block + 15 s). A host that raises Codex's
`background_terminal_max_timeout` to at least that yield sets the variable, and
`next --run` then covers up to that block per exec+poll pair (fewer `paused:`
reruns, each of which costs another pair). Every blocking command prints the same instruction as
its first stderr line before any work: until-terminal `host_run_status` (the text
default), foreground `host_run`, and `next --run`, which also streams one
short `ran: <reason> (<command>) -> exit <n>, <s> s[ runId=<id> | <status line>]`
line per executed step (stderr; the final text adds only a count). The text, owner
and constants live in `core/owner-wait-guidance.ts`.

`next --run` (run 17 Q6: 27 poll-only owner turns, a launch turn per managed run,
TEST authoring one step at a time) executes every `framework` step in order: gate
steps, `launch` steps (fully bound managed launches; all prepared lanes are
launched before the first wait) and `wait` steps. All waits of one call share ONE
budget (`--waitBudgetMs`, default and max 285000, or `PROOF_OR_STOP_OWNER_WAIT_BLOCK_MS`): each wait runs
`host_run_status --untilTerminal=true` with the remaining budget as `waitMs`, so
the call ends inside one owner yield (300000 ms by default). A `parallel` step
spawns its commands concurrently (one line per command, `[i/n concurrent]`). When the budget is used while the
run is still going, it prints `paused: wait budget of 285 s used; ... run
\`proof-or-stop next --storyId=<id> --run\` again` and the wait step. It stops at
the first `agent`/`human` step, a refused step (`stopped: step refused`), a launch
of a target it already launched in this call, or `--maxSteps` (default 40, max
100). The loop is `runNextSteps` in handlers/next-driver.ts; JSON output is
`{executed, stopped, paused, next}`.

"Repaired" is per finding (`managedFindingRepairState`, handlers/next-driver.ts): a managed `proof-or-stop-finding-repair` run whose immutable binding targets exactly that finding id (`managedDispatchTarget.findingId`), created after the finding was raised, completed as a safe delivery (`verifyManagedDispatchDelivery`), with a commit reachable from the Story HEAD, committed while that run ran and touching a non-metadata path. A grouped run (`remediation.grouping=single`, the default) is bound to every finding in its `groupFindingIds`; for each of them, the bound one included, the commit must also name that finding id in its message, so `next` never resolves a finding the grouped run did not demonstrably fix, and a member without such a commit gets its own single repair run. A material change since the finding's review is **not** enough: with several open findings, the repair of one changes the material of all (run 14 proposed `finding_resolve` for an unrepaired F-005 after F-004's repair). A completed bound run without such a commit gets the repair dispatch again, its `why` naming the run. This only chooses the step; a batched `finding_resolve` (`resolutions`) re-checks this per finding and records each finding's own commit. A finding the REVIEW inventory critic dispositioned `duplicate` of a canonical finding (same root cause) gets no repair cycle of its own while the canonical one is open (run 17 Q1): once the canonical finding is repaired and resolved, `next` proposes `finding_duplicate_resolve`, i.e. `finding_resolve` with `duplicateOf` (the canonical id) and `coverage: {command, selector}` the agent authors for the duplicate's OWN case (a test the canonical repair added for it, or its repro as a test). The framework runs that allowlisted command (executable + argv, project `validate.env`) in the Story worktree and closes the finding (`resolutionType: duplicate`, the receipt appended to the resolution) only on exit 0 with the selector in the output; a generic selector (`ok`, `PASS`) is refused. The critic label alone never closes it: a failed run is recorded in `duplicate-finding-coverage.json`, `finding_resolve` refuses `[duplicate_coverage_failed]` with `Next: proof-or-stop next`, and `next` then dispatches the duplicate's own managed finding-repair (its `why` names the failed run). A duplicate that already has a repair run bound to it follows the ordinary repair rule. The same closure applies to an open finding whose ReviewRun was superseded by a later run of its lane in the same round (the round was invalidated, e.g. by an unauthenticated commit that broke the managed live binding, and `review_round_prepare` reran the lanes) when a finding of that later run restates it (`supersededRestatementOf`; lab `reroute-mid-inventory`): the live copy is canonical and is repaired, the superseded copy closes only by its own coverage run; `finding_resolve` accepts `duplicateOf` for it. A superseded open finding no rerun restated is repaired on its own; neither is dropped. The same per-finding rule closes a repaired advisory (low or suspected) finding before REVIEW (run 16: a repaired low regression reached DONE open). After DONE, `finding_resolve` and `finding_dismiss` refuse (`<cmd> refused: Story <id> is DONE ...` and one `Next:`): a DONE Story's findings are part of its merged record, and a write from the integration checkout would stay uncommitted.

`review_round_prepare` routes the candidate specs itself. In a project without a requirements corpus (a Go task repo) it records the automatic full-scan reason; `understanding.touchpoints` count as protected sources only through the leading path token of a part that resolves to a real file, so free-text touchpoints ("ast/ast.go IndexExpression and String") never surface as `missing_protected_source` and never demand a `fullScanReason`. A stale full-scan route whose escalation was only the missing corpus (plus such pre-fix free-text reasons) reroutes with the plain command whoever wrote its reason (`isNoCorpusOnlyFullScan`, run 17); an owner reason is asked for only when the fresh route still escalates. An owner `candidate_spec_route` in REVIEW is refused when the stored route is still launch-ready and the current round already has a ReviewRun (`candidate_spec_route refused [candidate_route_current_in_review]`, nothing written, one `Next: proof-or-stop next --storyId=<id>`; lab `reroute-mid-inventory`): the material the lanes reviewed is unchanged, so it gives them nothing new, but it invalidates the round (the OPEN inventory epoch with `OPEN_REVIEW_INVENTORY_CANDIDATE_ROUTING_MUTATION`, the managed passes' live binding, then every lane reruns). Before, such a reroute after the lanes were imported and the critic completed ended in a REVIEW step with no command. A stale or missing route, a route before any ReviewRun of the round, a dry run (`persist: false`) and every phase other than REVIEW are unchanged (`candidateRouteLaunchReady`, core/candidate-spec-routing.ts).

PRE_CERT cheap check (run 17 Q5: `validate --focus=fast` and the routine
`validate` ran the same single configured command, 2 x 14.3 s). The rule
(`core/certification-window.ts` admission, `PRE_CERT_CHEAP_CHECK_REQUIRED`):
`certification_window_begin` admits only with a current signed complete PASS
from `validate --story --focus=fast --json` bound to the current head (or a
metadata-only lineage from it), material and story-files hashes; the admitted
window then permits exactly one routine `validate --story --json`, whose fresh
PASS the REVIEW→TEST gate consumes. The cheap check exists to fail fast before
a window is admitted. It is waived (`precertCheapCheckWaived`,
handlers/validation-identity.ts) only when the separate run proves nothing the
window's routine run does not: no validate.ts entrypoint (it receives `--focus`
as an argument), the fast plan is the routine plan
(`precertCheapCheckSubsumedByRoutine`: both from configured `validate.commands`,
neither full, identical source inputs, profile, verification policy, runtime and
normalized commands — executable, args, cwd, shell, timeout, optionality, focus
tags, effective environment and executable digests), no story-aware dynamic
validation mode in the environment or project config, and no
`validate.reuseFreshRoutinePass`. The routine run then still executes fresh
inside the window (the fresh-run requirement is unchanged), and while the waiver
holds it refuses an explicit `dynamicMode` or `reuseFreshRoutinePass`. Any other
plan keeps the cheap check, and `next` keeps proposing it.

Single host (run 14: the owner discovered the environment, probed, recorded the
fallback and pasted 3 `autopilot_review_submit` rounds by hand, ~5.2 min):
`quorum_submit --singleHost` keeps the assurance rule exactly. The round count and
hosts per round are the evaluators' own (review escalation: 3 rounds x 1 PASS host
with a degraded fallback; assurance floor: 1, or 3 after failure signals, x 1).
It writes nothing unless every required lane has a current signed reviewer pass
(the same `assertCurrentReviewerPasses` rule as the 3x2 quorum): each round
transcribes those reviews (`note` names the passes), never a self-attestation.
It refuses with the 3x2 quorum command when its probe finds two review-ready hosts
or an explicit high-risk policy disallows the degraded fallback. Probe, fallback
and the verdict batch keep their own authenticated metadata commits; it runs in
TEST only and is a no-op when nothing is missing.

Every command `next` prints is `proof-or-stop <command> '<JSON payload>'`. The CLI
also accepts that form followed by flags (`... '<json>' --json`): the flags merge
into the payload, and a flag restating a payload key with a different value is
refused. Before, the trailing `--json` made the CLI drop the JSON payload
(`argument_validation_failed: storyId undefined`, run 14).
`packages/main/tests/single-host-and-init-snags.test.mjs` scans every step call in
`handlers/next-driver.ts` and requires each to be a catalog command whose payload
keys are catalog fields and that parses with `--json` appended.

A payload or argument that does not parse prints ONE line, last, and no argument
help: `JSON parse failed: <parser message> near: <text around the position>[; a "
inside a JSON string value must be written \" (or avoid the quote)] (arguments:
proof-or-stop <command> --help)` (`printArgumentParseFailure`,
cli/help-renderer.ts). Before, the error came first and ~50 lines of help ended
with "Owner lease meta options: --takeover", so `| tail -2` in run 16 showed only
that footer and the owner retried 15 receipts as "lease contention". Schema
validation failures keep their bounded `Argument validation failed:` block
ending in `Next: proof-or-stop <command> --help`.

Managed launches reuse the host/model/effort of this Story's last managed run of
the same profile (reviewer or dispatch), falling back to the qualified managed
reviewer default; `host_run` still validates the selection. Only a reused
selection with all three set makes a launch `launch: true` (framework); the
default-only first launch stays `agent`.

`--run` executes only `framework` steps (gate steps, `launch` steps and waits),
each as a separate real CLI process with every gate in place, re-decides after
each, and stops at the first agent/human step, the first refused step (its
output tail is shown), a second launch of a target launched in the same call,
or `--maxSteps` (default 40, max 100); it pauses when the call's wait budget
(285 s, or `PROOF_OR_STOP_OWNER_WAIT_BLOCK_MS`) is used. A `parallel` step's
commands run concurrently, each a separate real CLI process. It is off by default.

One decision is one synchronous git observation (the same scope a single gate
evaluation uses): every identical read-only git probe the consulted gates make
(HEAD, material / story-files trees, merge-bases, branch and common-dir probes,
object-addressed blob reads) runs once per decision, and a row's own predicates
are evaluated only when that row is reached (the evidence chain is not built
while a finding still awaits repair). Nothing survives the call and nothing is
cached across calls. On the ND fixture this cut the child processes per
decision from DEV 75 / REVIEW 221 / PRE_CERT 257 / TEST 394 (max) to
22 / 83 / 124 / 161; `node packages/main/dist/tasks/next-driver-cost-smoke.js`
holds those budgets and requires every decision to equal the frozen
pre-optimization driver and the CLI's own `next --json`.

next --storyId=<id>`: an INVALIDATED certification window (before: the illegal

### Detection A/B variant switches (six experimental, default off; `review.round2Lanes`, `remediation.grouping` and `remediation.thread` adopted)

Nine project-config switches were added to measure, in a detection A/B, whether a
structural review/dispatch change loses findings (bench-staging run-17 cost
analysis §3; `implementation.thread` from the v41 cost plan item A1;
`review.lanePack` and `review.roundDelta` from its items A3 and A4). With no key in `proof-or-stop.config.json` every switch resolves to
its production value (the first value listed below).

- `review.round2Lanes` is **adopted** and is a production setting: later-round
  review lanes start fresh by default. The detection A/B V3 arm
  (bench-staging/oldpos/ab/results-r2.md, n = 4 per arm) found the post-repair
  seed 4/4 with fresh lanes against 3/4 with resumed lanes (the hard D4 seed 2/2
  vs 1/2) and cut round-2 lane input tokens by 56% (15.7M to 6.9M per round:
  resumed lanes start at 405–515 KB of context, fresh ones at ~105 KB); wall time
  did not change. `resume` restores the earlier behavior (rollback) and is
  recorded like any non-default switch.
- `remediation.grouping` is **adopted** and is a production setting: `next`
  repairs all open blocking findings of a round in ONE grouped finding-repair
  run by default (`single`). The detection A/B V4 arm (same results file, n = 4
  per arm) cut remediation wall time by 48% (3.1 vs 6.0 min per replay) and
  remediation tokens by 70% (1.1M vs 3.7M), with 1.0 repair runs per replay
  instead of 2.5. Every finding was still fixed (all final-tree repro probes
  pass, no round-2 lane re-reported a round-1 seed), the run made one commit per
  finding, each finding was resolved naming its own commit, critic duplicates
  were closed by coverage runs, and round-2 detection did not change (3/4 vs
  3/4). `per-finding` restores one repair run per finding (rollback) and is
  recorded like any non-default switch.
- `remediation.thread` is **adopted** and is a production setting: managed
  finding-repair runs start a fresh Codex thread with the framework repair pack
  (`fresh`) by default. Evidence: old-PoS run 25 (`implementation.thread=fresh`)
  repaired F-001 in a fresh thread for 0.86M input / 2.4 min, against 2.8–3.9M per
  repair resumed on the Story code-writer thread at 10–16M context in run 26
  (bench-staging/oldpos/run25-26-analysis.md §1.5). Implementer items keep
  `implementation.thread` (default `resume`). `resume` restores resumed repair
  threads (rollback) and is recorded like any non-default switch.
- The other six are **experimental** (A/B measurement only, not production
  settings) and default OFF, so the CLI behaves byte-for-byte as before.

The `commands[]` in `validate --json` is a validation receipt: structured commands are recorded in argv form by default; string configurations that contain shell semantics such as `cd`, `&&`, pipes, or redirects are recorded with `shell=true`, indicating a deliberate shell receipt. A required command failing causes validate to fail; an `optional:true` failure only warns. `doctor`'s Validation scan is advisory only: it shows the validate file, configured commands, fallback discovery, and the no-validator warning, to help you decide whether to add an explicit `validate.command(s)`.

Story-aware dynamic validation is selected with `proof-or-stop validate --story=B-xxxx --dynamic-mode=<mode> --json` (the `--story` flag is required for story authority). The supported modes are:

* `off`: run the configured complete validation plan with no dynamic selection.
* `observe`: compute and persist the signed selection manifest, then run the unchanged complete plan as the sole authority. It records the observe/full-plan oracle comparison and never launches a competing selected plan.
* `shadow`: execute the dynamic Wave-0/selected path and compare it with the complete-plan oracle; the complete result remains authoritative and dynamic receipts are not TEST/DONE authority.
* `enforce-low-risk`: may grant dynamic TEST authority only for eligible local/docs Stories after the current baseline, closure/runtime trace, receipt, scope, pinned-command, shard, revocation, and periodic-full prerequisites all pass. Otherwise it fails closed to the complete-plan fallback.

Long-running pinned verification commands use the separate `validate.evidenceCommandTimeoutOverrides` array. Each entry binds one positive finite `timeoutMs` to an exact allowlisted `command` executable and complete ordered `args` vector. These entries do not register commands in routine `proof-or-stop validate`; prefix, substring, and near-argv matches keep the 270-second evidence default. A malformed array or duplicate executable+argv identity fails closed to that default. The command-specific ceiling never bypasses the outer CLI deadline or its TERM→KILL→reap cleanup. Within one `verification_evidence_batch_add`, exact cwd+command duplicates share one execution, while every intent still evaluates its own immutable selector and receives its own receipt; any failed selector preserves the all-or-nothing checklist write.

When a signed/configured Git workspace is expected, including an explicit no-story `gitRoot`, failure to resolve that identity stops before callback entry instead of silently minting a split lock; genuinely non-Git projects retain their project-root identity. A second official validation prints `waiting for workspace validation capacity` with holder and heartbeat details on the progress/stderr side channel, then runs automatically after the holder releases. Story-scoped runs acquire this workspace lease before the existing per-story evidence lock. In-process reentrancy is bound to each acquisition's never-reused token, for both locks: a detached async context from a released owner cannot borrow a later holder's matching path. Unknown, malformed, or merely old capacity metadata is not reclaimed; reclaim requires mechanical local-dead or holder/heartbeat identity-mismatch evidence. A candidate is prepared with complete identity before its atomic queue publication; stale recovery atomically quarantines only the classified UUID ticket and never recursively deletes the shared capacity root, so a killed pre-publication process cannot block the queue and a replacement holder cannot be removed through an ABA path swap. Owner release and queued-waiter abort/deadline cleanup retry exact-ticket isolation. Persistent failure makes a best-effort released-marker write: when it succeeds, a successor can mechanically recover after filesystem repair; when it also fails, the ticket remains fail-closed until repair. A successful callback reports the release failure. If the callback or wait already failed, that original error remains primary and the secondary cleanup failure is not separately surfaced. Direct `proof-or-stop validate` enters the structured watchdog only to propagate abort/deadline into the capacity wait and clean its waiter ticket; it retains its existing result classification and exit contract. `structuredDoneResult` and the DONE-result classifier remain exclusive to `done_prepare` / `done_required_validate` and are not a `validate` result contract. Derived host-verdict binding has no public abort/deadline arguments; adding caller-controlled cancellation there remains outside this interface contract, so its CLI host timeout is still the outer cancellation boundary.

The checked-in regression contract includes a genuine exact-12 child-process stale/ABA cohort (distinct from the exact-12 in-process Promise cohort) and proves `maxConcurrency=1`, zero critical-section overlap, zero child errors, and zero queue-artifact leaks. This is a test/evidence contract, not a runtime concurrency guarantee for users. Its terminal and managed verification-pin contract is exactly `validate-execution-lock workspace capacity contract passed: 15 assertion groups` for the focused lane and `validate-execution-lock smoke passed: 26 assertion groups` for the full lane.

`capability_release_backfill` is a **record-then-bind migration** that links existing artifact releases and under-bound candidate playbooks to product capability releases. B-8128 enriches capability-release lineage at candidate-creation time, so candidates created before their story had a recorded capability release stay under-bound: `lineage.sourceStoryId` is set but `lineage.capabilityReleaseId` is absent. There are two reasons a story can be missing that binding, and the migration handles both.

```bash
# Default dry-run: list eligible under-bound candidates + a deterministic plan digest.
proof-or-stop capability_release_backfill --dryRun --json
proof-or-stop capability_release_backfill --dryRun --storyId=B-xxxx   # optional single-story filter

# Apply requires the current dry-run plan --digest (refuses on drift).
proof-or-stop capability_release_backfill --apply --digest=sha256:<planDigest-from-dry-run>
```

A candidate is **eligible** iff it is `status: candidate`, has a `lineage.sourceStoryId`, lacks `lineage.capabilityReleaseId`, and one of:

- **`plan: bind`** — a capability release already exists for the story (the candidate was just created too early). `--apply` binds the candidate to it.
- **`plan: record-then-bind`** — the story has an **artifact** release but **no** capability release (it DONE'd before the capability-release feature, so the DONE classifier never recorded one) **and** the capability classifier accepts the artifact release's `paths`. The dry-run reports the exact `PCR-…` it would record (id/version derived deterministically from the artifact release's paths + `artifactSetDigest`). `--apply` **records** that capability release into `.proof-or-stop/capability-releases.jsonl` (committed with `git add -f`, mirroring B-8128's DONE-merge ledger commit), **then** binds the candidate. If the classifier declines (paths do not declare a reusable capability) or the story has no artifact release, the candidate is conservatively **not** eligible — the migration never invents a binding.

`--apply` enriches only eligible candidates' lineage with `capabilityReleaseId` / `capabilityId` / `capabilityVersion` / `artifactReleaseId` (the same field set B-8128's enrichment sets). It is a deliberate, digest-guarded writer under the shared learning-store lock that **records** missing capability releases but **never** changes `.status` (candidate stays candidate), **never** touches `usage.surfacedCount`, and **never** appends a playbook-outcome. It is **idempotent**: after apply every story has a capability release and every candidate is bound, so a re-run finds `eligibleCount: 0` (no duplicate PCR). The recorded capability releases stay non-authoritative and never gate evidence.

## Finding identity, history and non-gate scorecard (Story 2)

`finding_candidate_add/get/merge/disprove/promote` preserve immutable detector
sources independently of suggested identity. Promotion links an existing verified
Finding through a current eligible signed REVIEW run and an actually executed,
candidate-bound reproduction receipt. Candidate creation preregisters the exact
reproduction executable, argument template, and candidate-independent selector;
promotion materializes the candidate marker into that template and requires the
signed receipt to match both the command and selector. The eligible reviewer must
also supply a semantic reproduction assertion; the CLI persists it as a signed,
non-gate `CandidateReproductionAttestation` bound to the exact candidate hash,
preregistered contract and selector, causal receipt hash, verified FindingRef,
and current review run. Caller-authored PASS text or a marker-bearing execution
receipt without that attestation cannot authorize promotion.
`finding_identity_confirm/query` distinguish suggestions from reviewer-confirmed
identities; an unknown cause is valid. `finding_supersession_add` and
`finding_identity_supersede` append exact signed correction trails, including
corrections owned by a current REVIEW Story to historical DONE observations.
They never rewrite the predecessor. Staged canonical revisions are not current
until their exact signed link is committed.

Target owners use `finding_route_accept/reject/revoke`; callers can independently
verify an exact receipt with `finding_route_verify`. A suspected-candidate receipt
is legal without promotion, a confirmed cause, GREEN, or a baseline set. An initial
accepted Finding-profile receipt atomically includes all four signed baseline kinds and
their set. `finding_candidate_route` separately binds the source to the latest
exact receipt/profile/hash. `finding_progress_predecessor` is a neutral source
checkpoint port, **not** proof of a valid Story 1 deferral. Real target-authorized
progress is captured with `finding_progress_capture`; unchanged code may accompany
genuine test, completed-delivery or status progress. Current consent is a separate
verification from historical signed bytes.

Use command-specific `--help` for the strict schemas. No command accepts arbitrary
Finding authority fields, caller baseline facts or caller target-owner facts.
Queries are available in every phase; source mutations and reviewer commands have
their independently registered role, phase, owner and cwd restrictions.

```bash
proof-or-stop finding_history_query '{"storyId":"B-03b7","sourceStoryIds":["B-03b7"],"package":"packages/main"}'
proof-or-stop finding_identity_scorecard '{"storyId":"B-03b7","sourceStoryIds":["B-03b7"],"mode":"observe"}'
```

History defaults to current observations; `includeSuperseded:true` explicitly
requests predecessors. Exact keys include path, package path, symbol, contract,
canonical identity, source lineage and outcome. The index and filtered query
projection have separate digests. Missing or corrupt input is incomplete/refused,
not an apparently complete empty result. Historical receipt invalidity may trigger
`finding_history_recall` exactly once for the canonical subject and actual changed
trigger, but never makes that receipt current consent or gate evidence.

The Story 2 scorecard returns all 14 declared record-kind counts (including zeros),
the exact verified signed semantic records and their ledger receipts, current
source bindings, a global canonical-catalog dependency digest, and a deterministic
projection digest. Pin `expectedInputDigest` to reject later source or foreign
canonical-correction drift. Reads never create a key or signature. The exported
`verifyIdentityScorecard` compares the complete response to a freshly trusted
current query, not merely to a caller-supplied self-consistent hash.

Per-detector/version/category promotion fractions are **descriptive adjudication**,
not precision or recall. They count each current terminal candidate once per
contributing detector family; an empty denominator reports
`observed:null,status:"insufficient_evidence"`. Historical signed rows do not
assert current consent. This is the Story 2 input contract for a future aggregator,
not Story 1's `finding_rollout_scorecard`, a qualification report or enforce permit.
The query's `mode` labels read-only report presentation; it is not a global policy
switch and does not disable separately authorized mutation commands. To run an
observe-only workflow, invoke only read/benchmark commands. Disabling its output
means stopping that reader. Persisted warn-style advice remains additive and the
existing Finding blocker predicate remains authoritative at every point; output
disable/re-enable never deletes records or silently rebinds stale consent.

### Verbatim request (`request.md`) and PLAN traceability

`story_create` accepts `request` (or `requestFile`, a path relative to the project root): the user's request verbatim, never a paraphrase. It is written to the Story's `request.md` (bounded to 16 KB; a longer text ends with `[proof-or-stop: request truncated at N of M bytes; ...]`), with `request.json` holding its sha256, source and amendment history. `request.md` is part of the INIT_CHECK signature domain; a Story without it keeps the previous signature.

```bash
# stage before the Story exists (wrappers, benchmark adapters); the next story_create consumes it once
proof-or-stop story_request_set --requestFile=/tmp/task.md
# record or amend for an existing Story (IDEA/INIT/INIT_CHECK/PLAN only)
proof-or-stop story_request_set '{"storyId":"B-xxxx","requestFile":"/tmp/task.md","amendmentReason":"<what the user changed or clarified, >=30 chars>"}'
```

Replacing a recorded request, or recording one after INIT, requires `amendmentReason`; it is appended to `request.json`. A `request.md` edited outside the command no longer matches `request.json` and is shown to reviewers as non-authoritative. `story_create` and `story_request_set` print the backticked request literals (examples, listed variants, exact messages) that no checklist title, `userSees` or `verificationIntent` states yet, with one exact `checklist_update '{"storyId":...,"itemId":"CHK-xxx","userSees":"<...>"}'` per item: `userSees` (like `verificationIntent`) is editable in INIT and PLAN and frozen from DEV, so the literals are recorded on the same Story and no Story is recreated. In PLAN, `next` lists any literal still unstated (or not named by an item's `excludes`) as part of its pre-scope `plan_authoring` step, before it launches the scope-plan reviewer.

`story_create` applies the PLAN intent-metadata rule to intake intents: every `verificationIntent` row carries `scope`, `expectation` and `requirementSource`, else `story_create REFUSED, nothing was written ... [verification_intent_metadata_required]` names each unclassified row and its missing fields (`CHK-001:happy:0 (missing requirementSource)`) and prints one copyable classified row. `checklist_update` (verification-intent roles, owner proposals) and `plan_acceptance_prepare` / `plan_acceptance_apply` refuse with the same text.

Pinned values the request does not quote carry a derivation (old-PoS run 23 at its source, `core/intent-derivation.ts`). With a recorded `request.md`, an intent row whose `desc` is an input -> output example (separator `->`, `→`, `=>`, `==`, else returns/yields/gives/prints/...) with a concrete expected value (backticked literals, else quoted strings, `[...]` / `{...}` groups, numbers) that `request.md` does not contain verbatim (case-sensitive, whitespace and backticks aside) must carry `"derivation":{"requestQuote":"<verbatim request.md sentence>","computation":"<steps from it to the pinned value>"}`. `requestQuote` must occur in `request.md` (case, whitespace and backticks aside; `...` may elide; at least 12 characters) and `computation` must state the pinned value. `story_create` (against the request it records, a staged one included), `checklist_add`, `checklist_update` and `plan_acceptance_prepare` / `plan_acceptance_apply` refuse a missing or invalid one: `<command> REFUSED, nothing was written ... [intent_derivation_required]`, one line per row (`CHK-001:happy:1 pins "[9,8,7,6,5,4]": no derivation`). A quoted example needs none. A row stored without one (the request was recorded or amended later) is a `missing_intent_derivation` blocker in `story_review`, and `next`'s `plan_authoring` gives the exact `checklist_update` with a `derivation` placeholder on that row.

In PLAN, the scope-plan dispatch prompt carries the request inline and requires one feature row per normative sentence, "for example" and enumerated variant; a row is covered only by a `userSees` or `verificationIntent` that states that exact variant or output, otherwise it is a gap. The same mechanical literal pre-check is listed there. The prompt also lists what is "Already covered" and never a gap (run 17): delivery-workflow sentences the Proof-or-Stop workflow guarantees (working on a branch from main, committing everything, merging back; `covered_by: "proof-or-stop-workflow"`) and restriction-only constraints the Story already acknowledges in its INIT `scopeBoundary.excluded` and `understanding.constraints` (`covered_by: "init-scope"`); every behavior, output, error, example and compatibility promise stays strict. The verification-intent prompt points at `request.md` and asks for one exact-output intent per example and listed variant, with a `derivation` on each expected value the request does not quote. The scope-plan prompt also carries the pin audit: every row pinning a value the request does not quote (ref, desc, requestQuote, computation), which the reviewer recomputes from the request; a mismatch is a blocking gap `pin-audit CHK-xxx:<lane>:<n>: pins <value>; request gives <value>`. While the prompt lists such a row, or the request has a same-semantics sentence, the scope-plan verdict is not deferred past DEV entry (v4.1 N8 exception, `scopeVerdictDeferral` = held): DEV entry waits for it, so the gap lands before any item is implemented against the pin. Its same-semantics rule requires, when a request sentence makes one behaviour follow another ("same ... semantics as X"), at least one intent whose input makes the plausible readings differ, else an `asymmetric-example: <sentence>` gap. `story_review` words both gaps as an intent fix (`checklist_update` with the corrected row and its derivation), then the reviewer rerun. Prompt cost: about 1.1 KB plus about 270 B per listed row. The INIT product reviewer gets the path only; REVIEW lanes and the critic get it inline (next section).

### The request outranks intents (old-PoS run 23)

Run 23 shipped a wrong behavior: the owner pinned a wrong expected value in a verification intent at INIT (`a[::-1]=[9..4] -> [9..4]`, while the request says "Use the same index-selection semantics as read slicing"). The implementer, two REVIEW lanes and the inventory critic each computed the contradiction and deferred to the intent ("the checklist is the requirement source"; the critic filed it as a "limitation (not a finding)"). Since lab `request-outranks-intent` (core/request-authority.ts):

- **REVIEW lanes and the critic get the request.** Every story-level REVIEW lane dispatch prompt (and so its managed assembled prompt) carries `request.md` inline (already bounded to 16 KB by `story_create` / `story_request_set`) plus the shared `REQUEST_OUTRANKS_INTENT_RUBRIC`: re-derive the expected value of every behavior the request specifies from the request text; a pinned intent, `userSees` or test assertion that contradicts the request is a finding of at least medium severity, even when the test passes; "the checklist is the requirement source" never resolves a contradiction with the request; the intent is followed only where the request is silent. This reverses the earlier rule that kept the request out of REVIEW lanes (token discipline): about +4.2k bytes (~1.05k tokens) per lane run on the abs request. A Story without `request.md` adds no bytes.
- **Critic.** The inventory critic's dispatch prompt carries the request, the rubric and `CRITIC_REQUEST_CONTRADICTION_RULE`: a divergence between the implementation, a pinned intent or a test and a request sentence is a finding (at least medium), never a note or "limitation"; a claim that two readings agree on a pinned case must show both computed outputs.
- **Implementer and finding-repair return an `[intent-conflict]` section.** Both prompts point at `request.md` and end with the mandatory section: `[intent-conflict] none`, or one line per conflict `[intent-conflict] <intentRef> | request: "<sentence>" | request implies: <value> | intent pins: <value>`. A "deliberate choice" that follows an intent over the request must be listed there; prose notes are not read. `next` parses the section from the terminal run's last assistant message (live-output.jsonl), and also treats an implementer's prose-only deliberate deviation (a "deliberate choice" sentence that names the intent, checklist, pin or request, or a stated deviation from / contradiction of the request) as a conflict on its bound item; an ordinary design remark is not one.
- **A declared conflict blocks.** In DEV (no implementer/repair in flight) `next` returns `intent_conflict`: `story_advance --phase=PLAN` (intents are frozen in DEV; `checklist_update` refuses `verificationIntent` there). In REVIEW, a refusal that would resolve repaired findings returns to DEV first (`intent_conflict_dev`). In PLAN it returns `intent_conflict_amend`: `checklist_update {itemId, verificationIntent, reason, status: "pending"}`; the revised row states the value the request implies (or, when the intent is right, its derivation from the request sentence), and the item is implemented again in DEV. A conflict counts as amended once the item's intent differs from the committed intent the run was dispatched against.
- **Repair keeps base behavior of input variants (run 24).** The finding-repair prompt adds `REPAIR_INPUT_VARIANT_RULE`: when the fix changes how an input is handled (null, 0, negative, empty, omitted vs explicit), run the finding's input and its literal variants on the Story base (the exact base SHA is printed) and on the fix, keep base behavior for every variant the request did not change, test the syntax node rather than only the evaluated value, and treat a reviewer "Fix:" as a non-binding suggestion. Run 24's grouped repair compared the evaluated index to NULL and turned explicit `null` into "omitted", which cost a third round.

### PLAN selected process-owner coverage

When ProofStory verification topology selects canonical `process-fact:<factId>` references, `scope_check_save` requires the registered scope reviewer and `ownerDispositions`. Each canonical registry path needs exactly one `{path, disposition, reason}` row: `modify` or `test` must match checklist files, while `unchanged` records substantive reviewed sufficiency (reason at least 40 characters). This does not authorize scope expansion or require edits to all consulted files. Repository-keyed evidence binds the selection, declarations, source bytes and relevant local-main source bytes. `story_review` and the direct PLAN-to-DEV guard revalidate it, independently of cached review counts. Invalid, stale, missing or tampered evidence blocks. Stories without selected canonical topology retain legacy behavior; this bounded check does not infer unselected features from prose or certify independent-host execution.

Inside a managed `proof-or-stop-review-scope-plan` run, `scope_check_save` binds the saved verdict to the live run (`deliveryRunId`). A later save of the same live run re-binds and replaces the earlier one (re-seal, as `delivery_check_set` does). A scope reviewer save that carries no `LATTICE_MANAGED_INIT_INVOCATION` while that Story/role has a running managed run binds only through the run's process group; otherwise it is refused with the variable named, never written unbound (old-PoS run 20: an `env -u LATTICE_MANAGED_INIT_INVOCATION` save overwrote the bound verdict with `deliveryRunId: null`). Every refused save is journaled on the run as `managed_dispatch_save_refused`; when the run would end `managed_dispatch_output_missing`, the worker first resumes the reviewer's own Codex session with that exact error (at most 2 turns, see host-run-usage.md).

Owner coverage conservatively binds all four registry projection input files (process-fact registry, command policy, process-fact levels, and flow-fact policy); any byte change in these inputs requires fresh review, even when an unrelated registry row changed. Unrelated main commits with identical relevant source bytes remain current.
