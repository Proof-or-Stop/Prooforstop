## Trigger Event
On 2026-07-24, cross-host finding B-bf52:F-062 (codex-cli host-B, final review round) reported that B-bf52's canonical product record is internally inconsistent even though the shipped code had no defect. CHK-003 of B-bf52 was proven undeliverable during review: distinguishing a lifecycle artifact ordinal from a volatile one is not achievable from message text alone, because embedded evidence.output is interpolated verbatim into a story_advance DONE rejection at core/machine.ts:1190, so a third-party TAP label such as bug-2 is the same string as a real artifact ordinal. Eight successive recognition rules were each broken by cross-host review before they were seen as eight measurements of one impossibility. The operator confirmed the scope shrinkage in .lattice/story/actives/B-bf52/scope-shrinkage-decision.json, yet CHK-003 still reads status done and AB-003 still asserts the behaviour the story proved impossible.

## Key Insights
The honest disposition of a planned item has three values, not two: delivered, not yet delivered, and legitimately withdrawn. The record currently has no way to say the third, so a withdrawal has to masquerade as a delivery. Two distinct questions are being confused. The checklist layer answers how a work item's final disposition is displayed and counted. The acceptance contract layer answers what the effective contract is after an original promise is legitimately withdrawn. They are different records with different authorities and must not be merged into one field, but they must agree: both cite the same scope-shrinkage decision id, and that agreement is validated in both directions. The PLAN freeze on proofstory_contract_set is deliberate and stays; the correction path is append-only, so the original binding remains readable forever and the withdrawal is a new record beside it rather than an edit of it. The 24 existing status === 'done' consumers, including the DEV to REVIEW gate at core/machine.ts:355, mean a new terminal status is a gate-visible change, not a schema tweak.

## Solution Tradeoffs
The request offered two options for layer 1: persist success so consumers render done(success=false), or add an explicit withdrawn status. Withdrawn status is chosen. A boolean hung off done leaves done as the stored value, so every one of the 24 done consumers that does not also read success keeps reporting the item as delivered, which is the exact failure being fixed; an explicit status makes omission visible instead of silent. For layer 2 the alternative was allowing proofstory_contract_set from DEV and REVIEW, which is rejected because it would let implementation rewrite its own acceptance promise, destroying the audit value of the PLAN freeze; an append-only withdrawal record keeps the original assertion intact. The main risk accepted is that withdrawal becomes a route to a formal PASS, so authority validation, cross-layer consistency, and a minimum-delivery-scope guard are treated as part of the feature rather than as follow-ups.

## Conversational Texture
The operator's framing was that the system must be honest: a withdrawal must be recorded as a withdrawal, must not be disguised as completion, and must not quietly rewrite the original PLAN promise. They explicitly asked that the two gaps be implemented as two layers linked by one decision id rather than as a single field change, and they emphasised that the last acceptance test matters most, that there must be a minimum delivery scope or re-approval mechanism so a story cannot obtain a formal PASS by withdrawing every requirement that turned out to be hard.
