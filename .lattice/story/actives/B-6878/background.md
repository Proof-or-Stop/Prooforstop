## Trigger Event
During B-30c3 a genuine Codex host-2 cross-review surfaced (F-001/F-002) that the own-property / null-prototype hardening applied to the codex+gemini PROVIDER extractors should be applied SYSTEMATICALLY across the rest of the usage ledger. The operator deferred that broader class to this dedicated story. The full threat model, a workflow-verified 48-surface inventory, the fix-strategy tradeoffs, and the scope boundary are written up in docs/requirements/decisions/usage-ledger-prototype-pollution-hardening.md (the PLAN source for this story).

## Key Insights
HONEST FRAMING — defense-in-depth, NOT a live vulnerability: adversarially verified (workflow 2026-06-19, three independent exploit-path checks) that there is NO reachable live exploit today. JSON.parse() does not mutate Object.prototype; a literal "__proto__" JSON key becomes a harmless OWN property; no in-repo code writes Object.prototype; and for openai/gemini, B-30c3 null-proto projection already neutralizes inheritance. Justified by (1) high consequence IF the precondition ever changes (the ledger is billing/usage truth; a future transitive dep/plugin/host runtime polluting Object.prototype would yield a silent bogus token count), (2) consistency with B-30c3, (3) a single audited chokepoint beats dozens of ad-hoc prototype-chain reads. SURFACE INVENTORY (line numbers may have DRIFTED since 2026-06-19 — re-locate by symbol): the ledger reads token fields off objects originating OUTSIDE it (JSON.parse of provider/CLI stdout, externally-supplied options) using `in`, dot/bracket reads, and `x ?? {}` defaults — all of which return an INHERITED value when the key is absent as an own property. Unguarded remainder (B-30c3 already hardened providers/codex-cli.ts + providers/gemini-cli.ts — do NOT redo): assemble.ts extractRawUsage `in` (most load-bearing entry) + options.usage default; dispatch-usage.ts anthropic extract (u.input_tokens/output_tokens/cache_*; envelope.model/usage); the four adapters anthropic/openai/gemini/shared usage reads + `in` checks; streaming.ts usage merge (largest cluster ~10 reads); record.ts validator `in`. Optional/lower: diagnostics.ts internal-table bracket lookups (NOT external parsed data).

## Solution Tradeoffs
CHOSEN (spec recommendation): Option 2 — a SINGLE null-prototype whitelist chokepoint (shared helper toOwnPropsNullProto(obj, whitelist) in adapters/shared.ts or a new usage-ledger/sanitize.ts) applied ONCE at the two entry points (extractRawUsage in assemble.ts, and the anthropic extract in dispatch-usage.ts), so every downstream adapter/streaming read operates on a null-prototype object carrying only whitelisted token keys (safe by construction). Generalizes exactly what B-30c3 shipped for codex/gemini and collapses ~30 surfaces to a handful. PLUS the cheap belt: convert residual `in` operators (assemble.ts, record.ts, adapters/openai.ts, adapters/shared.ts, streaming.ts) to Object.prototype.hasOwnProperty.call. REJECTED: Option 1 (per-read own-prop guards everywhere — ~30 sites, no structural guarantee); Option 3 (Object.freeze(Object.prototype) at process start — risks breaking deps, far outside the ledger boundary). NON-GOALS: do NOT change the B-253e validator (the usage-record validator that rejects non-numeric/negative token counts but accepts any valid number regardless of origin), the strict four-field accounting (the input / output / cache-creation / cache-read token bookkeeping), the anthropic/openai/gemini record shapes, or primaryReportedTotal visibility; do NOT redo the codex/gemini extractors.
