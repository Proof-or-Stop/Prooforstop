## Key Insights
The single largest failure mode of unsupervised multi-agent review is confident-but-wrong findings. §2.3 filters them with M skeptics under a refute-by-default rule (a Verdict defaults isReal=false; flipping to true requires concretely confirming the defect against the code) and a threshold-confirm rule that is deliberately NOT a majority: a finding is CONFIRMED iff confirms >= T, default T=1 of M=2 (one concrete proof suffices; the other skeptic's non-confirmation carries no disproving weight). A finding with confirms=0 is dropped and never counts. Separately, §4.2 fixes a mandatory LEDGER MAPPING: the methodology Finding severities (BLOCKER/MAJOR/MINOR) are NOT finding_add's enums (critical/high/medium/low) — passing an abstract severity to finding_add is a Zod error. The map is BLOCKER->critical, MAJOR->high, MINOR->medium (low for cosmetic); desc composes "<title> — <issue> Fix: <fix>" with the line cited inside; file->files '["<file>"]'; category in happy|edge|adversarial|missing; plus reviewRunId and a real lattice-review-* agent. The order is always verify -> MAP -> finding_add; only CONFIRMED findings are ever mapped+recorded.

## Solution Tradeoffs
Like S1, S2 is a pure-data + injected-seam module (new core/adversarial-review-verifier.ts) importing S0's Finding/Verdict/FindingSeverity verbatim. The skeptic is an injected (finding, change) => Verdict seam so the module is hermetically testable with a fake (no live review agent at MVP); the module only counts isReal verdicts and applies the threshold — the refute-by-default discipline lives in the skeptic prompt/role, not in the counter. T and M are parameters (defaults T=1, M=2) so the precision/recall tradeoff is tunable. The ledger mapping is a const Record + pure compose functions returning finding_add args (no I/O — the actual finding_add CLI call is the caller's/S4's job).
