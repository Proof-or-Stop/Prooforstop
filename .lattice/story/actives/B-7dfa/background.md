## Key Insights
The current red-evidence surface (red_evidence_create in packages/main/src/handlers/proofstory.ts, records in .lattice/story/actives/<id>/red-evidence.json) accepts a self-reported failingCommand/failure-count with no machine-checkable assertion envelope: nothing binds WHAT the RED run asserted, no runner proves the workspace was untouched (head/material/index/status four-tuple), records can be silently replaced rather than superseded, replays can duplicate records, and there is no owner-gated quarantine path for bad records. The program plan enumerates the five contract areas: (1) policy-owned assertion envelope (bounded matchers, minimum specificity, expected exit class, target-exercised proof, GREEN = exit0 + !timeout + pattern-absent + target-exists); (2) runner pre/post four-tuple invariance in a disposable workspace; (3) supersedes chain with closeout-grade integrity (monotonic seq + prior digest + fork rejection; latest = unique chain head); (4) idempotency key (recordId, materialHash, specDigest, policy/assertion digest, freshness-compatible head); (5) quarantine/recover as owner-gated registered operations creating NEW record IDs linked by recoversRecordId with immutability preserved, plus the corrected retention claim (canonical receipts preserve metadata freshness within a round only; review rounds are per-entry, transition-orchestrator.ts:663).
