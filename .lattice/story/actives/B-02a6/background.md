## Trigger Event
On 2026-06-19, while a fleet ran in parallel (B-59c7 / B-997b in PLAN, B-e28c in REVIEW), story B-0c17 was found with its core INIT metadata (index.json / background.md / checklist.json / init-check.json) wiped from the shared main checkout; only owner-lease.json + init-self-check.json remained. The user asked for the root cause so parallel development stops losing INIT work. This is the same data-loss family as the B-854c ClawCreek incident (19 lost stories).

## Key Insights
The safe-init-commit that makes story metadata clean-proof is created only at the INIT_CHECK bootstrap (worktree.ts ~348-360: git add -f -> write-tree -> commit-tree -> update-ref refs/heads/story/<id>), committing to the new story branch. A story still in INIT has its metadata as plain untracked files in the shared main checkout - committed to no branch, recoverable from no git object. .gitignore allowlists .lattice/story/actives/** (leaf NOT ignored), but allowlisted is not committed: a plain git clean -fd (untracked + not-ignored) or any working-tree-mutating op deletes it permanently. auto-commit-metadata.ts:182 returns early on the main branch, so story_create on main never commits. story-metadata-protection.ts:116-117 flags only ignored && !tracked, so the !ignored && !tracked INIT window is wrongly deemed safe. The selective survival is explained by post-wipe re-creation: the whole dir was removed, and the lease heartbeat + an init self-check re-wrote owner-lease.json + init-self-check.json afterward.

## Solution Tradeoffs
Approach A (chosen direction): create the safe-init-commit at story_create so INIT metadata is a durable, recoverable, clean-proof git object from birth, under the main-write-lock story_create already holds; the reverse purgeSafeInitCommit already exists for discard. Robust, mirrors the existing bootstrap machinery, closes the window against every destructive op (clean / checkout / reset / recovery). Cost: a small git commit/ref per story_create (even for soon-discarded stories), but discard already reverses it. Approach B (detection-only: extend the protection predicate + doctor warning) was rejected as the sole fix - it diagnoses but does not prevent the concurrent wipe. Approach C (hold a lock across the whole INIT->INIT_CHECK window, or write INIT metadata off the shared checkout) was rejected as heavier and changing the worktree/branch model. The protection-predicate extension (Approach B) is kept as a complementary defense-in-depth, not the primary fix.

## Conversational Texture
The user hit the wipe during a parallel fleet run and asked: what is the root cause, otherwise parallel development keeps wasting time. I traced the chain through auto-commit-metadata.ts (skips main branch), the INIT_CHECK bootstrap (first/only safe-init-commit), .gitignore (allowlisted but untracked), and story-metadata-protection.ts (predicate blind spot), confirmed B-0c17 was never committed (git ls-files empty), and proposed moving the safe-init-commit earlier to story_create.
