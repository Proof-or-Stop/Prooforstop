## Trigger Event
On 2026-08-14, story B-9ff1 (W2d of the red-evidence subsystem programme) completed all nine review rounds, closed forty-nine findings, recorded a full-3x2 quorum and ran all 100 configured validate commands green, yet could not enter TEST. Five successive root-cause attributions were made and falsified before measurement located the defect: isolatedBlobHash in packages/main/src/core/done-prepare-generated-metadata.ts reads a staged blob with execFileSync and no maxBuffer option, so Node's 1 MiB default applies. The artifact it must read, test-evidence.json, measured 1,369,692 bytes because packages/main/src/handlers/verifier.ts writes it as output equal to JSON.stringify of the full captured output of every configured validate command, and lattice.config.json validate.commands grew from 56 to 100 entries that same day.

## Key Insights
The failure is silent and its message is actively misleading. execFileSync throws ENOBUFS above the default buffer; the surrounding catch returns null; the caller compares that null against the expected digest and reports verified metadata changed after manifest verification. That sentence names concurrent modification, so an operator reasonably suspects another session, dirty metadata, or a timing race, and none of those is the cause. The behaviour was reproduced from first principles outside the repository: a fresh git init with a 1,400,000-byte staged file throws ENOBUFS under default options and returns all 1,400,000 bytes when maxBuffer is raised. It was also isolated inside the repository: the same commit path succeeded with fifteen-byte fixtures and failed only with the real oversized artifact, and a two-hundred-millisecond file watcher over the three managed paths showed no write at all inside the commit window, which eliminated every concurrency explanation.

## Solution Tradeoffs
Three separable concerns and each is addressed on its own terms. First, the immediate defect: every helper in this module that reads blob or tree content through execFileSync needs an explicit generous maxBuffer, not only the one that was observed to fail, because the others carry the identical latent limit. Second, the diagnosability defect, which is what made this expensive: a catch that converts an infrastructure failure into a value the caller reads as digest differs destroys the distinction between the blob is genuinely absent and the blob could not be read, and that distinction is exactly what a person needs. The repair must preserve the fail-closed posture while surfacing the underlying cause. Third, the growth cliff itself: storing the complete output of every configured command inside a lifecycle artifact means the artifact grows without bound as the suite grows, and the suite grew seventy-nine percent in one day. A digest plus a bounded tail preserves the evidentiary value while removing the cliff, and the full transcript remains available where it is already written. This story implements the first two and evaluates the third explicitly rather than deferring it silently.

## Conversational Texture
The blast radius is the whole repository rather than one story. Once the artifact crosses one mebibyte, persistStoryValidationEvidence can never commit, so no test-evidence.json is ever stored, so assessStoredValidationPassAdmissibility always reports evidence missing, so the REVIEW to TEST phase gate cannot be satisfied by any story. The fix is self-bootstrapping because a worktree runs the dist it builds itself, so this story's own gate exercises the repaired code once it compiles. Not in scope: the separate hard-coded 900 second phase-gate timeout budget, which is a real and distinct asymmetry against done_prepare's config-derived budget and is being handled on its own.
