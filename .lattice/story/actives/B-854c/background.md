## Trigger Event
On 2026-06-15 a ClawCreek user (Lattice 0.3.5) lost ALL 19 stories' metadata: a routine git operation (rebase that did checkout origin/main, where the untracked paths did not exist) deleted .lattice/story/actives/*/* leaving only owner-lease.json; git ls-files .lattice was empty and git check-ignore .lattice showed not-ignored ('neither tracked nor ignored'). Files were unrecoverable from git history. Verified bootstrap path at worktree.ts:316 (git add without -f) and this repo's protective allowlist at .gitignore:9-18.

## Key Insights
The defect is a conflation of two lifecycles under one ignore prefix: volatile runtime (locks/, runtime/, traces/, activity.jsonl, tmp/) vs persistent story metadata (index/background/checklist/decision/plan) both live under .lattice. A broad `.lattice/` ignore protects the volatile parts from git clean but silently untracks the persistent metadata; a no-ignore stance tracks metadata but lets git clean / wrong-branch checkout delete it when untracked. The bootstrap's `git add` (no -f) further breaks when .lattice is ignored. There is no scaffolding or validation of the negation allowlist, so safety depends entirely on each user hand-crafting .gitignore correctly.

## Solution Tradeoffs
Approach A (force + validate): use git add -f in bootstrap AND add a check-ignore guard + clear error/repair when story metadata would be ignored. Approach B (scaffold/validate .gitignore): on init / via doctor, write or verify the ignore-volatile/track-metadata allowlist so new projects are safe by default. Approach C (relocate): move volatile runtime out of the .lattice metadata prefix (or metadata out of a broadly-ignored prefix) so the two lifecycles stop colliding. A and B are additive and low-risk; C is cleaner long-term but a layout migration. This needs a real design decision (preMortem required) because it is a data-loss/critical path; the chosen model must make bootstrap git-add and the protection stance consistent.
