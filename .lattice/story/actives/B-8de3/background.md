## Trigger Event
On 2026-07-10, the follow-up audit for B-70e9 finding F-012 (concurrent appendUsageRecord corrupted the usage-ledger hash chain; fixed with an mkdir-based lock in packages/main/src/core/usage-ledger/writer.ts) swept all appendFileSync call sites and last-line-dependent writers under packages/main/src for the same TOCTOU class and found this same-family defect in packages/main/src/core/evidence/artifact-store.ts.

## Key Insights
writeArtifact() has two coupled weaknesses. First, the immutable object objects/sha256/<digest>.json and the ref refs/by-id/<artifactId>.json are written with plain writeFileSync, which is not atomic: a crash mid-write leaves a truncated JSON file on disk. Second, the dedupe path is existsSync -> readFileSync -> JSON.parse -> return, so once a truncated object exists, every later writeArtifact call with the same content throws on JSON.parse forever - the write branch is skipped because the file exists, so the store never self-heals and readArtifact via the ref also fails. Concurrent same-digest writers hit the same window transiently (writer B parses writer A's half-written file): repro-intake CLI commands are not covered by the validate execution lock, so main-agent plus subagent invocations can overlap. Integrity matters here because repro-intake artifacts feed the repro-evidence-binding DEV gate. The rest of the audit was clean: process-events.jsonl, activity.jsonl, health.jsonl, review-loops.jsonl, the evidence observed.jsonl event ledger, dev-memory, and cross-host-review host-verdict events are all pure appenders with no tail dependence; the artifact-release and capability-release idempotent-append checks are serialized by the DONE-merge flow; the queue exception registry read-modify-write is a rare operator action on non-authoritative advisory data.

## Solution Tradeoffs
Adopt the repo's existing atomic-write idiom - write a uniquely named tmp file in the same directory, then renameSync into place, as playbook-runtime-memory-cache.ts and playbook-runtime-memory-index.ts already do - for both the object and the ref writes, and make the dedupe path recover from an unparseable existing object by atomically rewriting it from the current payload instead of throwing forever. A cross-process lock like the usage-ledger fix is deliberately NOT needed: objects are content-addressed, so concurrent writers of the same digest produce identical bytes and atomic rename makes last-writer-wins harmless. Out of scope: adding hash chaining to observed.jsonl (a pure append-only informational log) and any locking of the ledger append itself.
