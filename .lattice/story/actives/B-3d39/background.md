## Operator Impact

What broke: when two Lattice stories run in parallel and one reaches DONE while another hits INIT_CHECK in the same process, the DONE story can be silently marked DONE but never merged to main — the operator must manually `git merge` to recover (hit twice this session). What changes: the in-process lock reentrancy becomes async-context-aware so concurrent stories correctly contend instead of one skipping the lock, restoring the "DONE means merged" invariant; plus a 2-line guard fix restores a heartbeat-only warning that was silently suppressed.

## Trigger Event

User directive (2026-06-18): after the test-infra convergence work, the user asked whether a trustworthy CI gate makes parallel multi-story development more trustworthy. A read-only root-cause investigation of three parallel-dev friction points found that the highest-severity one is a real, intermittent data-integrity bug: a DONE story can be marked DONE on its branch but never merged to main, requiring manual git merge recovery (observed twice this session: B-be91 and B-2941). The investigation overturned the surface framing (it is NOT a worktree-remove ordering problem) and pinned the actual root cause to an in-process main-write-lock reentrancy race.

## Key Insights

- ROOT CAUSE (git-reflog-proven): the reentrancy registry heldLockPaths in packages/main/src/core/main-write-lock.ts:271 is a bare process-global Set. Its own doc comment states the load-bearing (wrong) assumption: "Within a single Node process JS is single-threaded, so two critical sections can only interleave by direct function nesting." That holds only for SYNCHRONOUS nesting. The DONE merge lock is acquired at transition-orchestrator.ts:290 via acquireDoneMainMergeLock (defined done-effects.ts:268, which wraps acquireMainWriteLockRegistered in main-write-lock.ts) and HELD ACROSS the orchestrator's await points (runDonePreMergeGate, runPhaseChangeHooks, applyDoneMergeEffects). When DONE yields at an await and a CONCURRENT INIT_CHECK for a different story runs in the same Node process (parallel-wave / autopilot drive multiple stories per process), INIT_CHECK calls into the same lock, sees the DONE flow's key already in heldLockPaths, mis-classifies itself as a nested reentrant caller, SKIPS real acquisition, and commits straight to main. That foreign commit advances main HEAD mid-merge, so the story's --no-ff merge never produces its commit.
- REFLOG EVIDENCE (B-2941): 59ceec0d0 "merge story/B-2941: updating HEAD" produced NO merge commit; 21s later 08250a289 "lattice: INIT_CHECK metadata B-a4e3" committed straight to main; then 35a26c748 was the operator's MANUAL git merge (bare default message, not the framework's "merge: B-2941 <title>" format). B-be91's DONE merge happened to complete cleanly the same session, confirming the bug is concurrency-timing-dependent (intermittent).
- The on-disk mkdir cross-process mutex is SOUND and must stay untouched. Order-of-ops in applyDoneMergeEffects (done-effects.ts:677-905) is correct (merge BEFORE worktree-remove); worktree-remove failures are caught locally and cannot abort the merge. The defect is purely the in-process reentrancy classification.
- The framework already ships done_recover (handlers/done-recover.ts, detectPartialDoneStories) which CURES the partial-DONE state post-hoc — so maintainers already recognize "DONE but unmerged" as a real failure mode. The gap is PREVENTION of the race, not another cure.
- SECONDARY (tiny, same theme): the global-fallback guard checkGlobalFallback in core/codex-adapter-checks.ts:644 only probes for @lattice-agent/core in the global npm root, but the actual installed global link is @koala-agent/core. So the warning that is SUPPOSED to fire ("global lattice resolves to main's dist, not the current worktree; treat as heartbeat-only") silently never triggers — removing the one built-in signal that would have explained the materialHash-freshness friction the operator hit repeatedly. A ~2-line fix restores it.

## Solution Tradeoffs

- (a) Make reentrancy async-context-aware via AsyncLocalStorage (chosen direction). Two viable implementations to pick in PLAN/DEV: (a1) store the held-set inside an ALS run-context so concurrent async siblings each see an empty/separate set; (a2) keep heldLockPaths process-global but record an owner TOKEN per acquisition in ALS, and treat key-present as reentrant ONLY when the current ALS context owns that token. Both preserve genuine synchronous nesting (DONE->audit: audit inherits DONE's ALS context -> same token -> pass-through) while making concurrent siblings correctly contend on the on-disk lock. (a2) is the safer/more precise design because it keeps the cross-process mutex bookkeeping identical and only refines the "is this MY lock?" predicate.
- (b) Serialize the parallel-wave so two stories never share a process window: small (a few lines) but only MASKS the defect; rejected.
- (c) Rely on done_recover post-hoc: already exists; it is a cure not a prevention; rejected as the primary fix (kept as the safety net).
