## Trigger Event

While closing story B-49d4 (which removed a check bound to a fixed allowlist rather than to the property it guaranteed), a read-only investigation was run against main to test a suspicion about the INIT_CHECK gate. A first draft of this story was written, reviewed, and DISCARDED because its central claim was wrong. This is the corrected version; the correction is recorded here because the wrong version is the intuitive one and the next reader will arrive at it too.

The INIT_CHECK gate requires two named reviewers (`REQUIRED_INIT_CHECK_AGENTS = ['lattice-review-story-init', 'product-reviewer']`, packages/main/src/core/init-check-gate.ts:32) to have recorded a result before a story leaves INIT. Coverage and blocking issues live in `agentResults` inside `.lattice/story/actives/<id>/init-check.json`, and the file carries an integrity `_hash`.

## Key Insights

The gate decides on two things read from that file: `missingRequiredInitCheckAgents` (init-check-gate.ts:80-85) and `blockingInitCheckIssues` (consumed at core/machine.ts:1154). Neither is covered by the signature.

`signInitCheck` (init-check-gate.ts:133-143) signs exactly `storyId : backgroundHash : title : description : checklistHash : reviewRound : INIT_CHECK_SALT`. Both `agentResults` and `issues` are absent from that domain. A comment above the function lists intentionally-omitted fields (`agentId`, `issues`, `checkedAt`) but never mentions `agentResults`, which was added later and inherited the exclusion silently.

THE CORRECTION. The discarded draft claimed a two-step laundering primitive: edit the file to inject `agentResults`, which invalidates `_hash`, then make one legitimate `init_check_set` call whose carry-forward re-signs the injected data into validity. That is wrong, and the truth is simpler and worse. `signInitCheck` and `recomputeInitCheckHash` (init-check-gate.ts:133-172) never take `agentResults` as input, so editing `agentResults` does not invalidate `_hash` at all — the stored hash still matches the recomputed one, because the recomputation never depended on that field. No second call is required. A hand-edited file is accepted by `canEnterInitCheckGuard` with ZERO subsequent `init_check_set` calls. There is nothing being laundered; the signature simply does not protect the field the gate decides on.

The read path compounds rather than causes this: `store.readInitCheck` (core/store.ts:566-572) is a bare `readJson` with no `_hash` verification, and the `init_check_set` handler carries `previous.agentResults` forward from that unverified file (handlers/init-check.ts:138-142). That matters for a second reason given below, but it is not what makes the tampered file pass.

WHAT IS EXPLICITLY NOT IN SCOPE. A single caller can invoke `init_check_set` twice with two different registered `agentId` values and satisfy the two-reviewer requirement alone. That is BY DESIGN and must not be changed. EXP-001 established that main-agent and subagent are not mechanically distinguishable from inside a Bash invocation, so `init_check_set` deliberately does not validate `agentId`; CLAUDE.md states this stance explicitly. Four smoke tests positively assert that single-process accumulation SUCCEEDS: packages/main/src/tasks/init-check-required-agents-smoke.ts:103-115 and :139-140, init-check-fallback-smoke.ts:230-231, and test-flow-e2e.ts:391-392. An independent reviewer verified all four citations. No signature change can close "one caller legitimately calls twice", and attempting it would remove load-bearing behaviour. This story addresses only the integrity gap: data no legal caller ever wrote must not satisfy the gate.

WHAT IS STILL UNPROVEN. Every code fact above was verified by direct file reads, twice, by two different readers. The end-to-end behaviour — that a story whose `init-check.json` has hand-edited `agentResults` actually advances past INIT_CHECK — is still an inference from those facts and has NOT been executed. The first checklist item exists to prove or refute it, and every later item is conditional on that result.

A second consequence needs the same treatment: the merge constructs its output without the `fallback` audit block written by `init_check_repair` (handlers/init-check.ts:144-152). The block is lost after the very FIRST ordinary `init_check_set` call — one call before the coarser `initCheckAttestationMode` label flips from `fallback` to `independent` — so the durable record of a human manual attestation disappears before the label that advertises it does.

## Solution Tradeoffs

The existing corpus is the cost driver, and the design must argue its choice rather than let it fall out of the implementation. All figures below were measured at commit c59f9c0113 and WILL drift as sibling stories merge; re-derive rather than trusting them, by walking `.lattice/story/actives/*/init-check.json` and joining each to its sibling `index.json` `phase`. The counts are stated so the argument can be checked, not so they can be copied.

At that commit: 637 files total, phase split DONE 613 / DISCARDED 13 / INIT_CHECK 8 / INIT 1 / unreadable-index 2. `canEnterInitCheckGuard` returns early for any non-INIT phase (core/machine.ts:440), so ONE story is operationally gated and the rest are an audit and replay concern. The question is therefore not "is the corpus too expensive to invalidate" but "do we accept one operational break or ~636 audit breaks", which are different kinds of cost deserving different arguments.

Two facts constrain any migration. First, `agentResults` has six distinct on-disk shapes, not the four a first pass suggests: canonical pair 417, `koala-*` pair 173, `lattice-*@fallback` pair 21, `koala-*@fallback` pair 16, five files with three entries carrying historical actors, and five files with NO `agentResults` at all, where `initCheckAgentResults` (init-check-gate.ts:71-78) synthesizes a single-element array from top-level `agentId`/`issues`. Signing a synthesized value is not the same as signing an absent field, and the normalization must state which it does.

Second, and much larger than a first pass suggests: registry-invalid actors are not a handful of exotic ids. `koala-review-story-init` — the pre-rename name — appears in 179 `agentResults` entries plus 16 `@fallback` entries and is absent from `AGENT_DISPATCH_REGISTRY` entirely (verified by grep: zero occurrences). Together with the named historical actors (`codex-init-reviewer` x2, `codex-cli-init-reviewer`, `init-reviewer-A-r7k2m9`, `codex-host`), roughly 195 of 637 files carry an actor that would now throw `agent_dispatch_actor_unknown`. That is about 30% of the corpus, not the ~5 files a cursory look finds, so no migration can re-sign the corpus by routing through the handler, and any design that assumes it can is unimplementable.

There is also a governance consequence. core/command-policy.ts:396 marks `init_check_set` `ownershipClass: 'reviewerWrite'`, exempt from the owner lease, with the stated justification that it is "bound by its INIT signature gate". If the gap is confirmed, that exemption rested on a premise this story falsifies, and it should be re-argued rather than left standing on a reason that is no longer true.

## Conversational Texture

The operator's original framing was wrong twice over, and both errors are instructive. First, the suspected defect was "one caller can accumulate two reviewers" — investigation showed that behaviour is deliberate, documented, and asserted by four tests, so closing it would have removed a load-bearing invariant while leaving the actual hole open. Second, the replacement framing described an elaborate two-step laundering primitive; an independent draft reviewer showed the signature never covered the field in the first place, so no second step is needed and the defect is plainer than the story told about it. Both times the error ran in the same direction: constructing a mechanism sophisticated enough to be interesting, when the real finding was that a check simply was not there.

That same reviewer also found the first draft had frozen volatile counts into its own prose — the exact stale-number pattern the immediately preceding story existed to remove. This version states measurements with their commit and the means to re-derive them, and any later reader who finds these numbers stale should treat that as expected rather than as a defect.

The standing instruction for this work is to run each item through to DONE without pausing for approval. That makes repro-first discipline more important, not less: with nobody checking the intermediate reasoning, an unexecuted inference must be labelled as one and proven before anything is built on it. Checklist item 1 is therefore permitted to refute the premise and force a re-scope of the rest, and is not written as a formality.
