## Key Insight

The gate is mode-agnostic by design (evaluateDecompositionGate NEVER reads cfg.mode — confirmed by B-986c's smoke); §4.4 says the mode check lives SOLELY in the caller. So machine.ts is the only place that turns a provable block into an actual PLAN->DEV refusal, and only under mode==='block' (advise/off never hard-block — advise is Story 4's advisory surfaces). The single most important correctness property: the new sub-check must be FAIL-OPEN. canStartDevGuard's outer try/catch is fail-CLOSED (a broken/absent review blocks DEV), but the parallel-decomposition sub-check must be wrapped in its OWN try/catch that on any error FALLS THROUGH TO ALLOW — never returns false. Spec §4.8: the gate fails open on its OWN infrastructure errors (config load failure, unreadable own contract); a config typo or a transient read error must not strand every story at PLAN. getGuardFailureReason must mirror the same predicate so the decision and the message never diverge.

## Tradeoff

Fail-OPEN vs fail-CLOSED for the new sub-check: fail-closed would be 'safer' in the abstract (block on doubt), but here it inverts the gate's purpose — the gate exists to stop PROVABLE false-parallel assertions, not to block on its own inability to evaluate; a fail-closed infra error would make a config mistake brick the whole workflow. We take FAIL-OPEN (spec §4.8). Re-export vs leave-skeletons for the contract: re-export makes parallel-decomposition.ts the genuine single source of the frozen interface (its whole point), at the cost of a type-only import edge with the impl modules (no runtime cycle since type imports are erased). We re-export. Shared block->message helper vs duplicated logic: machine.ts already duplicates guard logic between canStartDevGuard and getGuardFailureReason; we add a small shared predicate/helper for the parallel block so the boolean decision and the human message cannot drift.
