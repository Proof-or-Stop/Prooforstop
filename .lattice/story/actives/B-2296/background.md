## Key Insights
Source findings F-027 / F-060 (checklist userSees) and F-059 (plan.md claims) share one failure mode: the claim text stayed frozen while the underlying code/evidence drifted. The dangerous signal is therefore NOT "the claim text changed" (ordinary review sees that) but "a frozen claim stayed static while the code it asserts about moved under it." A digest of the claim text alone catches neither incident. So the binding is bidirectional: bind each userSees claim to { normalizedClaimDigest, materialHash, headHash, attestedAt } at attestation time; drift in EITHER the normalized claim text OR the bound material (rename-aware) voids the attestation and requires re-attestation. Normalization is purely mechanical (trim + collapse whitespace) — no semantic diffing, because meaning-preserving-vs-changing judgment is the primary false-positive engine and belongs only in the Phase-2 human re-attestation.

## Solution Tradeoffs
Phase 1 is deliberately detect-and-report only and NON-blocking: adding a blocking gate before the re-attestation recovery path exists would wedge every story with a drifted userSees. Scope is userSees only. OUT to Phase 2: the blocking gate, reviewer re-attestation recovery (the implementing agent cannot self-attest), forced re-execution for executable-tied claims, and the legacy-unbound migration policy (grandfather DONE stories, require re-attestation on reopen, migrate active stories at the next gate). OUT to other stories: plan.md DoneWhen/Verify general drift (B-7813 already reconciles plan.md on the declare-unreachable path). NOT B-1507 (verification_run + refresh re-execution + PreToolUse). NOT B-3b88 (self-contradictory rows + refresh_stale laundering). Shipping detect+report first proves the false-positive rate on real stories and de-risks Phase 2, matching the program's cheapest-first, ships-independently philosophy (spec §3 / §6).
