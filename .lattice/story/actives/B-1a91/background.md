## Key Insights
applyDoneMergeEffects (handlers/done-effects.ts ~890-896) already runs auto-bump + auto-rebuild post-merge under the main write-lock; the finding-signals re-derive (deriveFindingSignalsFromStore in core/finding-signals.ts, persists via learning-store to the canonical MAIN cache post-B-37b3) is the natural never-throw third effect, run every DONE merge so experience accumulates per story. BUT a never-throw auto-refresh can silently fail or be skipped; to make it TRUSTWORTHY the cache must carry a COVERAGE WATERMARK (coveredStoryCount / coveredFindingCount / coveredThrough on the FindingSignalsCache type) and learning_validate must report the GAP between the persisted cache watermark and the current store, so a behind/missed cache is detectable. Lattice story ids are B-xxxx hashes (NOT a 438-style integer), so the watermark is a coverage count plus a max-timestamp, not a literal story sequence number. Recovery is the existing full re-derive (learning_scan), which closes any gap; the watermark turns silent rot into a loud, recoverable signal.

## Solution Tradeoffs
Two cohesive halves of ONE trustworthy auto-accumulating cache: (1) a never-throw advisory re-derive in applyDoneMergeEffects after the merge (every DONE; advisory status line; never blocks); (2) a coverage watermark on the cache plus a learning_validate gap report. Run the refresh on EVERY DONE merge (findings accrue regardless of code change). Watermark = counts plus max finding timestamp (plus optional covered-id digest); gap = persisted-cache-watermark vs current-store. All advisory-only; no gate reads the cache. REJECT a cron/CI schedule (unreliable, misses the just-merged story) and a pre-REVIEW agent step (depends on memory) — the DONE-merge hook is the reliable place, and the watermark is what makes its never-throw safe.
