## Trigger Event

User directive (2026-06-18): after B-348d shipped an OPT-IN `retryOnAnyFailure` allowlist as a documented STOPGAP for four smokes that intermittently FAIL (exit 1, not timeout) under heavy parallel `npm run test:all` load, the user asked to solve the deferred shared-state root cause NOW rather than leave the band-aid. A reproduction under amplified parallel load (20 concurrent smoke processes) surfaced the exact failure: `review_pass_set` exits 1 with `timed out waiting for metadata lock (EEXIST mkdir .../<story>/review-passes.lock)`, thrown from `field-regression-cli-smoke.ts`'s `assertReviewPassConcurrentCliSurface`, which fires five concurrent `review_run_start` + five concurrent `review_pass_set` CLI calls against one story. This is the real multi-reviewer REVIEW scenario.

## Key Insights

- Three handlers hand-roll their own mkdir-based metadata lock loops: `withReviewPassLock` (packages/main/src/handlers/finding.ts ~line 38), `withReviewRunLock` (packages/main/src/handlers/review-run.ts ~line 21), and `withInitCheckLock` (packages/main/src/handlers/init-check.ts ~line 67). All three use `deadline = Date.now() + 5000` (a 5s total acquire budget), a fixed 50ms poll, and a 10s stale-reclaim threshold; the critical section runs `autoCommitStoryMetadata` (a git commit) while holding the lock.
- The shared primitive `withMkdirLock` (packages/main/src/core/mkdir-lock.ts) already exists with `DEFAULT_DEADLINE_MS = 30000` and `DEFAULT_STALE_MS = 10000`, and its doc states the required invariant: the acquire deadline MUST be greater than the stale threshold so a waiter is still polling when a crashed holder's lock turns stale and can reclaim it. The three hand-rolled loops VIOLATE this (deadline 5s < stale 10s), so their stale-reclaim branch is effectively unreachable within a single waiter's window.
- `checklist.ts`'s `withChecklistLock` already delegates to the shared `withMkdirLock` (B-6812); the shared helper was literally extracted from the old checklist lock so others could reuse it. finding.ts / review-run.ts / init-check.ts were never migrated.
- Under heavy parallel load, several concurrent reviewers serialize on the per-story lock while each holds it across a git commit; commits slow down under CPU/IO saturation, so the tail waiter exceeds the 5s budget and throws -> the smoke FAILs. This is a real product robustness defect: multi-reviewer REVIEW on a loaded machine can spuriously fail, not merely a test artifact.
- Empirically confirmed: with the budget bumped 5s->30s, 8 concurrent field-regression-cli runs plus 8 filler smokes produced 0 failures (vs 2/24 failures at 5s under lighter load). The 30s budget absorbs the serialized sub-second commits.

## Solution Tradeoffs

- (a) CHOSEN: migrate the three hand-rolled lock loops to the shared `withMkdirLock` primitive (30s deadline, correct deadline>stale invariant, holder.json diagnostics), exactly as checklist.ts already does. Removes ~60 lines of duplicated, subtly-buggy code and fixes the load-induced FAIL at the source. Lock paths and external semantics are unchanged; only the timeout message wording changes (no test asserts on the old wording).
- (b) Just bump the literal 5000 to 30000 in each loop: fixes the symptom but keeps three copies of duplicated lock code and the deadline>stale invariant remains an unguarded local constant. Rejected in favor of de-duplicating onto the audited shared helper.
- (c) Move the git commit out of the critical section: would shrink hold time but expose concurrent commits to git index.lock races (a different failure), and the commit-inside-lock correctly serializes per-story commits. Rejected as out of scope.
- (d) Do nothing and keep the B-348d retry stopgap forever: leaves a real product robustness defect (multi-reviewer REVIEW can spuriously fail under load) and a permanent band-aid. Rejected.
