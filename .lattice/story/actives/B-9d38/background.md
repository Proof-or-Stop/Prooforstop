Program B-impl Story S3 of the adversarial-review build program (docs/adversarial-review-spec.md §2.4 + §4.3), opened 2026-06-20 after S2 (B-2806, per-finding verifier + ledger mapping) reached DONE+merged (lattice 0.3.31) and S1 (B-97ab, lens runner) before it. S3 is the completeness-critic role: the distinguished lens that asks "what did the review MISS?" and whose findings re-enter verification.

## Key Insights
The per-facet lenses (S1) structurally miss the integration surface: a 5th door (another path to the same sink), an unverified claim (a registration/test/gate asserting coverage it lacks), a modality not run (a config/profile the review never exercised), an interaction (two changes each fine but wrong together). The completeness critic (§2.4) hunts exactly that. It runs at ONE fixed point in the canonical order: AFTER the lens raw findings have been adversarially verified, so its input confirmedFindings is the VERIFIED set (never raw noise). Its contract is frozen in S0: CompletenessCriticInput {change, confirmedFindings} in, Finding[] out. Critically, its output is NOT privileged: each critic finding is itself raw and goes through the same S2 adversarial verification before it counts; a confirmed critic finding may REOPEN the round. For provenance (§4.3): Lattice counts reviewer evidence only when the finding agent startsWith lattice-review-, and there is no lattice-review-completeness lane today, so a confirmed critic finding MUST be recorded with --agent set to a REAL review lane (recommended lattice-review-quality or lattice-review-behavior) bound to that lane reviewRunId, with the [completeness-critic] provenance carried in the --desc (NOT in --agent — putting completeness-critic in --agent stores it as non-reviewer provenance and it would not count as lane evidence).

## Solution Tradeoffs
Like S1/S2, S3 is a pure-data + injected-seam module (new core/adversarial-review-critic.ts) importing S0 (CompletenessCriticInput, Finding) and S2 (toFindingAddArgs, FindingAddArgs) plus review-run REVIEW_RUN_LANES read-only for the lane type. runCompletenessCritic(input, runCritic) applies an injected (input)=>Finding[] critic seam to {change, confirmedFindings} and returns the raw critic findings unchanged (unprivileged); the critic role itself (the real agent) is supplied by the harness/main agent at MVP. A COMPLETENESS_CRITIC_DESC_TAG ([completeness-critic]) plus toCriticFindingAddArgs(finding,{reviewRunId,agent,category}) wraps S2 toFindingAddArgs and prefixes the desc with the tag, while typing agent as a REAL ReviewRunLane so the compiler rejects completeness-critic in --agent (§4.3). OUT OF SCOPE: the lens runner (S1), the verifier/threshold itself (S2), and the round/reopen ESCALATION loop incl. actually running verification on critic output, calling finding_add/review_run_start, and re-binding reopened rounds (S4). A dedicated lattice-review-completeness lane + a structured provenance field stay FUTURE (§4.4).
