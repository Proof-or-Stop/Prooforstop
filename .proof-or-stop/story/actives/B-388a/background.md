## Trigger Event
On 2026-07-27, B-4043 was found stuck at review_escalation_status assuranceLevel:missing after 5 review rounds, despite its process-events.jsonl ledger containing 12 host_verdict records forming two complete 3x2 quorum submissions (runIds B-4043-q-r1/r2/r3, submitted once at an older materialHash and again after a benign main drift where storyFilesHash stayed unchanged). A RED reproduction using the real evaluateReviewEscalation function (imported directly from packages/main/dist/core/review-escalation.js, no mocks) with a hand-built event fixture matching this exact ledger shape confirmed validRoundCount=0/3, with all three rounds reporting 'duplicate host/session/key identity' -- the identical failure mode observed live on B-4043.

## Key Insights
The root cause is in core/host-independence.ts's evaluateHostVerdictRounds: it collects ALL host_verdict events sharing a runId (after eventsWithStoryFilesHashDowngrade has rewritten stale-but-storyFilesHash-matching verdicts' materialDigest to the current value, without deduplicating the historical entry), then runs a union-find grouping keyed on (hostId, sessionId, keyId) to detect hosts faking independence. Because quorum_submit derives sessionId/keyId deterministically from (storyId, hostId) rather than per submission instance, a genuine re-attestation by the SAME host produces a verdict sharing the FULL identity triple with its own earlier (now-downgraded) entry. The grouping logic cannot tell 'the same attestor confirming again' (benign, should supersede) apart from 'two differently-named hosts sharing one identity key to fake independence' (the actual fraud signal, a PARTIAL key overlap). It currently treats a FULL-triple match exactly like fraud, permanently invalidating the round. A spike (packages/main/src/tasks -- to be added) proved: deduplicating by full (hostId, sessionId, keyId) triple match before the union-find grouping (later occurrence supersedes, since the ledger is append-only and chronological) fixes the benign re-attestation case while an adversarial fixture (two DIFFERENT hostIds sharing one session/key) still correctly gets flagged as invalid.

## Solution Tradeoffs
The fix is scoped to evaluateHostVerdictRounds only: dedupe verdicts sharing the exact same (hostId, sessionId, keyId) triple within a runId (keep the latest by ledger order) before running the existing union-find fraud detection, which is left untouched for partial-overlap cases. This does not touch quorum_submit's write-time duplicate guard, eventsWithStoryFilesHashDowngrade's downgrade semantics, or the round-number scheme -- those are out of scope and working as designed. B-4043 itself is explicitly out of scope for this story; it can be unblocked independently via the degraded-single-host fallback path using fresh, never-used runIds, since only the q-r1/r2/r3 full-quorum slots are poisoned on its ledger.

## Conversational Texture
The user's own framing, verified correct: 'the floor counts by round, the quorum resubmit guard dedupes by material, and the two disagree -- so the gate's own recommended remediation manufactures an unsatisfiable state.' More precisely: the resubmission/independence check dedupes by IDENTITY (not material), and that identity scheme is round-number-scoped and host-deterministic, so the very re-attestation the gate's own advisory recommends collides with and poisons the round it was meant to save.
