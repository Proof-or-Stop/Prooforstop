## Trigger Event
On 2026-08-28 the user asked to migrate the functionality of ~/work/repo/proof-or-stop-graph into this repository as one of the proof-or-stop commands. That directory is a real, working, self-contained package (@proof-or-stop/graph 0.1.0, 32 commits, HEAD 10b5921 "Style every scrollbar; give the playback rail room for its own", no git remote configured) which today can only be run from its own checkout. A grep across this repository finds no reference to proof-or-stop-graph anywhere except one runtime log line under .lattice/runtime/host-runs/, confirming the tool is presently invisible to this project.

## Key Insights
The source package was authored for exactly this migration. Its README carries a "Migration into Proof-or-Stop" section stating that src/index.ts is the library surface and that createApp() and startServer() are the seams a CLI command would call, and that nothing depends on the package's own shell. It already follows this project's Core/Shell convention, and its tsconfig.json matches packages/main byte for byte on the settings that matter (target ES2022, module Node16, moduleResolution Node16, strict, rootDir src, outDir dist, declaration), so it is a drop-in for the recursive tsc gate that both validate --lint and .githooks/pre-push run over every tsconfig.json in the repository.

Two facts discovered while scoping shape the work more than the copy itself. The search index imports DatabaseSync from node:sqlite, which is used nowhere else here and needs Node 22.5 or newer, yet no package.json anywhere in this repository declares an engines field, so this subpackage becomes the first consumer of that constraint. And packages/main ships zero static web assets today - its serve dashboard is an inline template literal in packages/main/src/verifier/serve.ts, it has no files field, and tsc does not copy non-TS files into dist - so the browser client cannot be routed through the packages/main build and must be served from packages/graph.

## Solution Tradeoffs
Three placements were considered. Merging the source directly into packages/main was rejected: it would mix a 9325-line web shell with CLI logic in one package and place a 4.6MB vendored asset tree inside the package that every command loads. Consuming @proof-or-stop/graph as a published npm dependency without moving the code was rejected: the code would stay outside this repository's validate and recursive tsc gates, and would need publishing or file: linking to be usable. The chosen option is a new packages/graph workspace subpackage with packages/main holding only a thin command handler that calls the existing library surface - the boundary the source README already anticipates - which keeps the large asset tree and the web shell out of packages/main while still placing every line under this repository's recursive tsc gate.

On the vendored browser bundles the user was direct: they are build output of npm dependencies and do not belong in source. They stay gitignored and are regenerated by the build, matching the source repository's own .gitignore, which excludes assets/ with a comment explaining that app.html is assembled by scripts/build-web.mjs and the vendor bundles are copied out of node_modules, so tracking them would only create merge conflicts.

The command name was chosen as the bare "graph" over story_graph and over proof_graph (the name the source README speculatively mentions), for the shortest form consistent with the existing serve, status and doctor commands. Because a bare name has no underscore prefix, help grouping does not derive automatically and needs an explicit KNOWN_GROUP and KNOWN_ORDER placement.

## Conversational Texture
The user's framing was migration, not redesign: move what already works into the CLI so it is one command away instead of a separate checkout. When asked how to handle the vendored bundles the user pushed back on the question itself, saying in effect that these have always been packaged from dependencies and of course do not enter source, treating build output staying out of source as obvious rather than a decision worth deliberating; the story therefore records it as a constraint rather than an open tradeoff. The user chose the subpackage boundary and the bare command name, and the value they expect is concrete and visible: running one command inside this repository and getting a browsable graph of its stories, with search and per-story detail, without dirtying the worktree that Proof-or-Stop gates DONE on.
