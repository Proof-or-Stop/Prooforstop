## Trigger Event
While recording verification evidence for story B-3144 (worktree .../B-3144), pinning `node packages/main/dist/tasks/quorum-submit-smoke.js` via `verification_evidence_add` was killed at [270.4s] with "pinned command exited 124 (timed out) but result:pass was claimed" ([receipt_exit_nonzero], checklist.ts:650) - despite lattice.config.json budgeting that exact command at timeoutMs: 1200000 (20 minutes, lattice.config.json:85; raised by commit c15e6dc8 "chore(validate): raise quorum-submit-smoke budget to 20m" after a measured 617s runtime under load). Two unfiltered reproductions in this environment measured 356-360s - well under the configured 20-minute budget but over the 270s ceiling the evidence tool actually enforces.

## Key Insights
verification_evidence_add / _batch_add / verification_run derive their mechanical receipt via runSingleAllowlistedCommand (validation-executor.ts:584-596), which builds its ValidationCommand with `timeoutMs: options.timeoutMs ?? DEFAULT_VALIDATE_COMMAND_TIMEOUT_MS` (270_000ms, line 595) and never consults lattice.config.json's validate.commands[].timeoutMs override. All four call sites in checklist.ts (lines 1557, 1648, 1779, 1858) invoke it as `runSingleAllowlistedCommand(command, root, { cwd })`, never threading a timeoutMs. By contrast, lattice validate's own path (runValidationCommand, line 311, called from executeValidationPlan, line 625) calls resolveCommandTimeoutMs(command, defaultMs) (defined lines 72-80), which reads command.timeoutMs when present - this is the ONLY place the per-command config override is honored today. The existing regression smoke validate-command-timeout-smoke.ts covers resolveCommandTimeoutMs and the lattice validate path in depth (explicit/zero/negative/injected-default cases, process-group kill semantics) but never touches runSingleAllowlistedCommand at all, so this gap has no regression coverage. The gap is structural: any validate command whose configured timeoutMs exceeds 270s AND whose genuine runtime also exceeds 270s can pass lattice validate cleanly while being permanently unable to earn a mechanical receipt through the evidence-pinning tools. A reusable normalizer already exists - configuredValidationCommands(projectRoot) (handlers/verifier.ts:224-258) - which flattens both validate.commands[] config shapes (bare string vs {command,args,timeoutMs,...}; schema at config.ts:198-211) into ValidationCommand[] with .command/.args/.timeoutMs already resolved, matching what resolveCommandTimeoutMs needs.

## Solution Tradeoffs
(1) Look up the pinned command in configuredValidationCommands(root) by matching parsed {executable,args} against each entry's {command,args}, and pass the matched .timeoutMs (else DEFAULT_VALIDATE_COMMAND_TIMEOUT_MS) into runSingleAllowlistedCommand's options.timeoutMs - mirrors resolveCommandTimeoutMs exactly, reuses the existing config normalizer, no new schema (chosen direction). Matching key needs a design decision: strict command+args equality (low false-positive-match risk) vs. also allowing label match (looser, risk of matching the wrong configured entry). (2) Raise DEFAULT_VALIDATE_COMMAND_TIMEOUT_MS globally - rejected: defeats the purpose of a low default ceiling that guards against hung commands; would let genuinely-hung commands run 4-5x longer before every evidence call, not just the ones with a deliberate override. (3) Require every caller to pass timeoutMs explicitly per pinned command - rejected: pushes the config-lookup burden onto every call site / future caller instead of doing it once centrally, easy to forget.
