## Trigger Event

On 2026-09-02 the repository owner set a standing rule: no AI-host attribution may enter git history, and by 2026-09-04 that rule extends to enforcement on both hosts. An audit on 2026-09-02 found 67 pushed commits carrying a Co-Authored-By trailer naming a host and 20 carrying a Claude-Session line. The rule was re-broken by every new session because the harness re-injects the attribution instruction per session, so a prose rule cannot hold. On 2026-09-03 a hand-written .githooks/commit-msg (commit 68b1f02b8a) started stripping trailers at commit time, but it depends on core.hooksPath, which git does not propagate on clone. Repro probe rp-mtmmuqiq-c9umc3 (review rr-mtmmuz5s-y4yhap) confirmed the second half of the gap on the same day: .claude/hooks/english-only-guard.cjs prints a warning and exits 0 for a git commit whose message contains CJK, and getCodexHooks() registers no English guard at all, so the Codex host never inspects such a commit.

## Key Insights

Host PreToolUse hook files under .claude/hooks and .codex/hooks are tracked in git and are read by the host from .claude/settings.json and .codex/hooks.json, so they survive a clone with no local configuration; the git-level hook does not. PreToolUse hooks can block: proof-or-stop-scope-pretool.cjs and proof-or-stop-evidence-pretool.cjs already exit 2, and english-only-guard.cjs is warn-only by its own choice, not by limitation. The two layers cover different holes: a PreToolUse hook sees the command string an agent issues, so it cannot inspect a git commit -F body, a human commit, or the CLI auto-commits made during a phase transition, while the git commit-msg hook sees every commit but only where hooksPath is set. Two independent CLI reviews of the 2026-09-03 design found three defects in the first commit-msg hook (unanchored patterns deleting prose lines, trailer-only messages emptied, whitespace rewritten on every message); all three were reproduced and fixed, and the lesson is that three separate regex copies will drift unless one fixture set is run through all of them. The policy boundary must be attribution metadata only, never host names as subject matter: 115 pushed commit subjects name a host while describing real adapter code, so a blanket word ban would block ordinary adapter work.

## Solution Tradeoffs

Blocking (exit 2) versus warning: warn-only produces no backpressure because an agent ignores stderr on exit 0; blocking forces the agent to rewrite the message, at the cost of one refused tool call. The owner chose blocking for both guards. One shared predicate versus per-hook copies: the hooks must stay self-contained (no dist import, the constraint english-only-guard already documents), so the predicate lives in core as data and each hook carries a byte-equal mirror pinned by a keep-in-sync test, the same technique the CJK_RANGES sync already uses. Keeping the git hook versus removing it: kept, as the host-neutral fallback for commits no PreToolUse hook can see, and held to the same fixture table. Rewriting the 87 pushed commits was rejected by both external reviews and by direct experience: a byte-preserving rewrite on 2026-09-02 invalidated every reviewer prompt envelope on the in-flight story and cost a full lane re-run.

## Conversational Texture

The owner asked why a git-level hook was chosen when the framework already generates host hooks into .claude and .codex that travel with the clone, and was right. The first answer relayed the external reviews too literally and claimed PreToolUse could only warn; the repository disproved that. The owner then asked for a story with explicit RED and GREEN checks per item and asked that english-only-guard be made blocking in the same change. Every checklist item therefore states the check that fails on main today and the same check passing after the fix, and red_evidence_create binds each RED before its fix lands.
