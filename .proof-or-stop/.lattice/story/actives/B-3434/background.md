## Trigger Event
On 2026-08-14, story B-9ff1 (W2d of the red-evidence subsystem programme) completed all nine review rounds, closed forty-nine findings, recorded a cross-host review quorum and ran all 100 configured validate commands green, yet could not enter TEST. Five successive root-cause attributions were made and falsified before measurement located the defect: isolatedBlobHash in packages/main/src/core/done-prepare-generated-metadata.ts reads a staged blob with execFileSync and no maxBuffer option, so Node's 1 MiB default applies. The artifact it must read, test-evidence.json, measured 1,369,692 bytes.

## Key Insights
The failure is silent and its message is actively misleading. execFileSync throws ENOBUFS above the default buffer; the surrounding catch returns null; the caller compares that null against the expected digest and reports verified metadata changed after manifest verification. That sentence names concurrent modification, so an operator reasonably suspects another session, dirty metadata, or a timing race, and none of those is the cause. The behaviour was reproduced from first principles outside the repository: a fresh git init with a 1,400,000-byte staged file throws ENOBUFS under default options and returns all 1,400,000 bytes when maxBuffer is raised. It was also isolated inside the repository: the same commit path succeeded with fifteen-byte fixtures and failed only with the real oversized artifact, and a two-hundred-millisecond file watcher over the three managed paths showed no write at all inside the commit window, which eliminated every concurrency explanation.

## Solution Tradeoffs
Where the size comes from, stated precisely because an earlier draft of this document got it wrong. Per-command output is ALREADY bounded: trimOutput in packages/main/src/core/validation-executor.ts truncates each command's captured output to MAX_OUTPUT_CHARS, twelve thousand characters, before it reaches the command result. What is unbounded is the AGGREGATE: packages/main/src/handlers/verifier.ts serialises every command result into test-evidence.json, so the artifact grows with the NUMBER of configured commands. One hundred commands at up to twelve thousand characters each is consistent with the measured 1,369,692 bytes, and lattice.config.json validate.commands grew from 56 to 100 entries in a single day. Raising maxBuffer therefore moves the cliff rather than removing it.

Three separable concerns, each addressed on its own terms. First, the immediate defect: every helper in this module that reads blob or tree content through execFileSync needs an explicit generous maxBuffer, not only the one observed to fail, because the others carry the identical latent limit. Second, the diagnosability defect, which is what made this expensive: a catch that converts an infrastructure failure into a value the caller reads as digest differs destroys the distinction between the blob is genuinely absent and the blob could not be read, and that distinction is exactly what a person needs. The repair must preserve the fail-closed posture while surfacing the underlying cause. Third, the aggregate growth itself, which must end in a BINDING outcome rather than a written opinion: either the artifact is bounded in this story, or a committed rationale records why unbounded growth is acceptable and names the change that will address it. Alongside that, the cliff must be marked rather than merely moved: the repository already has a threshold-classification model in buildLedgerSizing in packages/main/src/core/proofstory.ts, and the same shape applies here so an operator gets a visible advisory as the artifact approaches the limit instead of meeting a silent wall.

## Conversational Texture
The blast radius is the whole repository rather than one story. Once the artifact crosses one mebibyte, persistStoryValidationEvidence can never commit, so no test-evidence.json is ever stored, so assessStoredValidationPassAdmissibility always reports evidence missing, so the REVIEW to TEST phase gate cannot be satisfied by any story. The fix is self-bootstrapping because a worktree runs the dist it builds itself, so this story's own gate exercises the repaired code once it compiles. Not in scope: the separate hard-coded 900 second phase-gate timeout budget, which is a real and distinct asymmetry against done_prepare's config-derived budget and is being handled on its own.
