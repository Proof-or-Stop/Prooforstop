## Trigger Event
On 2026-07-25 the cross-host requirement audits of the evidence-integrity program (docs/evidence-integrity-program-spec.md) ranked evidence-binding mismatch (class ①) as the highest-value fix: it produced ~1/3 of the B-bf52 burn's findings and is the engine of the runaway-review-rounds class. Concrete recurring findings: F-049/F-050 (a pass row whose command named the wrong suite), F-045 (cited a test case that does not exist), F-061 (cited the wrong case within the right command). It is an interface defect — VerificationIntentItem (packages/main/src/core/types.ts:203-212) stores no command/selector, and the only binding predicate is evidence.intentRef === ref (packages/main/src/core/verification.ts:46-47) — so the tool asks the agent to assert a match it cannot mechanically check, then trusts it.

## Key Insights
The proof unit is (command, selector), not command: 16 of 19 evidence rows in the burn shared one command and only a free-text case name distinguished intents, so a bare expectedCommand field would not have caught F-045/F-061 — the selector (a test id / case name / assertion string that MUST appear in captured output) is what makes each intent's proof distinguishable. The strongest design is not validation but execution: if the tool runs the declared verifier and stamps the receipt, a false command cannot be authored at all — the error becomes impossible rather than merely caught. The intent is frozen from DEV and the implementation does not exist at PLAN, so the (command,selector) pair cannot be required up front; pinning it on the first evidence write and freezing it thereafter needs no foreknowledge yet makes later drift mechanically impossible. type manual|docs cannot execute and must be marked non-mechanical and not scored equal to receipts, or they become an escape hatch around the whole mechanism.

## Solution Tradeoffs
Execute-and-stamp (chosen) over a bare expectedCommand string field: the latter is insufficient (would not catch the case-name confusions) and still trusts result:pass. All the machinery already exists — validation-executor.ts spawn/executeValidationPlan runs a command in an isolated process group and captures output; done-required-validation.ts already produces a tool-owned receipt with exactly the fields evidence lacks (exitCode/outputDigest/outputTail) — so this reuses proven parts rather than building a new executor. Scope is deliberately the enforcement floor (schema + pin + execute-on-write + refuse-on-mismatch + manual/docs demotion + migration): the verification_run ergonomic command and the PreToolUse seatbelt are a separate follow-on so this story stays a reviewable, shippable unit, and refresh_stale is left to its own in-flight story (B-3b88) to avoid a two-session collision on the same file.

## Conversational Texture
The operator's framing across sessions: the agent keeps breaking its own process rules and the fix must move enforcement out of memory and into the tooling. The requirement audits corrected the original aim (a narrow quorum patch) toward this: make the correct action the path of least resistance and make the incorrect one impossible, not just discouraged. The operator wants each program step shipped as its own auditable Lattice story, cheapest first, dogfooding the very evidence gates being hardened.
