## Trigger Event
On 2026-08-14, following story B-3144's DONE (main commit 77301aa239; B-3144 aligned quorum_submit's duplicate-guard with the review-escalation floor's drift-accept predicate and added a quorum_prune recovery command), the user asked whether B-3144's hard-won lessons (fingerprint-pin propagation across multiple files, effectiveEnvironmentDigest baking in ad-hoc env vars, a test fixture silently defused by an unrelated sibling fix) were captured anywhere in Proof-or-Stop's own dev-memory system, or whether the capturing mechanism itself was missing. Investigation (two Explore-agent research passes) established: the mechanism exists and is well-designed (packages/main/src/core/dev-memory.ts, packages/main/src/handlers/dev-memory.ts, packages/main/src/core/playbook-runtime-memory.ts), the storage is git-tracked and genuinely shared (.lattice/dev-memory/experience.jsonl is NOT gitignored, unlike playbooks.json/signature-registry.json), and the READ side already auto-attaches a 'Memory Runtime Preflight' pack to most command output today. But the WRITE side is 100% voluntary: grepping every lifecycle handler (story-advance.ts, finding.ts, done-prepare.ts, done-closure.ts, done-effects.ts, transition-effects.ts, summary.ts, review-run.ts) for dev-memory references returns zero matches, command-policy.ts explicitly disclaims gate authority for every dev_memory_* command ('non-authoritative', 'never satisfies lifecycle gates'), and canFinishGuard (core/machine.ts:876-943, the actual DONE gate) never references dev-memory at all. There is even a self-referential dev-memory entry (id 7ffe281) reminding sessions to run preflight/capture -- itself proof the mechanism relies on an agent remembering a convention buried in a list of 16 entries, not on any enforcement. Across an entire multi-hour session that day spanning several other stories (an evidence-integrity design/audit arc, a review-deadlock investigation, and a merge-lineage classifier fix, in addition to B-3144 itself), dev_memory_capture was never called once until the user asked about it directly at the very end.

## Key Insights
The user's actual requirement, stated precisely and repeated three times to make sure a partial fix wasn't mistaken for a complete one: (1) lessons already in dev-memory must actually get consulted DURING development, not just be theoretically available; (2) a pitfall hit DURING development must actually get written back into dev-memory, not just theoretically capturable. A DONE-gate-only enforcement (requiring dev_memory_finish_decision before DONE) was explicitly evaluated and found to satisfy neither goal precisely: it doesn't touch the read side at all (that's already handled, informally, by the existing preflight auto-attachment), and on the write side it only forces ONE reflection checkpoint at the very end of a story -- for a long multi-round story (B-3144 alone spanned 6 REVIEW rounds and many hours), a single end-of-story attestation risks lumping or forgetting intermediate lessons, exactly the failure mode this story exists to prevent. The three-gate design (INIT_CHECK preflight requirement + finding_resolve advisory + DONE finish_decision requirement) was chosen specifically because each of the three lifecycle moments maps to a distinct part of the user's two-part requirement: preflight-before-DEV is the 'read' half, the finding_resolve advisory is the in-the-moment 'write' trigger, and the DONE requirement is the backstop that catches whatever the in-the-moment trigger missed.

## Solution Tradeoffs
The INIT_CHECK preflight gate is a HARD requirement (mirrors the existing pattern for scope_boundary_set/execution_boundary_set/scope_freeze_check, all of which already gate INIT_CHECK) because reading prior lessons before writing code is cheap and has no legitimate reason to skip. The finding_resolve reminder is explicitly NON-BLOCKING (advisory text appended to output, like the existing Memory Runtime Preflight pattern) rather than a hard gate on every single finding_resolve call, because forcing a capture-or-explicit-decision on every finding (some stories have dozens) would either produce noise (junk captures to satisfy the gate) or become an ignored ritual exactly like the DONE-only version this story is meant to improve on -- an advisory nudge at the moment of highest context (right after resolving a finding, while the fix is fresh) is judged to convert to real captures better than a blocking gate would, without the noise cost. The DONE-gate requirement mirrors summary_set/delivery-check's existing pattern (required, but an honest negative answer is accepted) rather than requiring a minimum COUNT of captures, specifically to avoid incentivizing fabricated/padded entries just to clear a numeric bar -- the goal is honest reflection, not volume.

## Conversational Texture
The user asked this as a direct architectural question after watching an entire multi-hour session generate several genuinely reusable lessons that never made it into the project's own shared memory system, only into Claude Code's private local memory (which does not help other sessions/agents working on this same repo). The user explicitly rejected a first draft answer (DONE-gate-only) as insufficient by re-stating both original goals a second and third time, until the gap between 'DONE-gate enforcement' and 'actually read during dev + actually write during dev, not just at the end' was made concrete and explicit. This story's design is the result of that back-and-forth, not a first-pass answer.
